# Основа первого рабочего каркаса

Дата: 3 ноября 2026 года. Подтверждённые продуктовые требования — desktop, наземная 2.5D симуляция, ориентир 10000+ объектов на больших картах. Типичная нагрузка зависит от игры, поэтому целевое оборудование, бюджет тика и доля активных объектов определяются измерениями сценариев.

**Границы сборок.** Core содержит независимые игровые типы. Content преобразует YAML в типизированные определения и зависит от Core и DeclarativeContent. Headless зависит от Content. Godot стенд использует тот же Content и компилирует файлы адаптера из `src/OpenRTS.Godot`. Отдельная assembly адаптера появится, когда потребуется второй Godot потребитель. Это не скрывает Godot зависимости внутри ядра.

**Инструменты.** Собственные проекты используют .NET 10 и Godot.NET.Sdk 4.7.2 — версии доступного окружения. `global.json` фиксирует SDK 10.0.105 с обновлением до последнего patch этой feature band. Импортированная DeclarativeContent сохраняет net8.0 и C# 12. Поддержка более старого runtime для самого OpenRTS не заявляется до отдельной проверки. Экспорт desktop сборок — отдельный этап проверки; успешный локальный запуск на macOS не подтверждает экспорт на Windows и Linux.

**Контент.** Нужны собственные RTS определения поверх неизменённого импорта DeclarativeContent. На первом этапе есть только Health. Каталог сортируется по ID с Ordinal сравнением. Контрольный отпечаток — SHA-256 бинарного потока: версия формата Int32, количество определений Int32, затем ID и MaxHealth каждого определения. BinaryWriter записывает целые числа little-endian, строки — UTF-8 с префиксом длины в байтах. Этот отпечаток сравнивает загруженные определения между хостами; он не является хешем состояния симуляции или форматом реплея.

**Графический стенд.** Godot создаёт 10000 статических маркеров через один MultiMesh. Число маркеров задаётся параметром стенда и не входит в игровые определения. Предел 1000000 защищает этот диагностический запуск от случайного чрезмерного выделения ресурсов, а не ограничивает движок. Маркеры размещаются в отображаемой сетке; их float координаты не определяют будущую численную модель симуляции.

Единственный MultiMesh пригоден для проверки пакетного отображения. Для большой карты потребуется пространственное разбиение: один MultiMesh имеет общую область видимости. Переключение на 10000 Nodes для этого не требуется. Выбор размера чанка принимается по измерениям видимой доли карты.

**Проверки.** Унаследованы исполняемые тесты DeclarativeContent. Проверки OpenRTS охватывают инварианты определений, наследование, отбраковку неверного контента и независимость отпечатка от оформления и порядка файлов. Сквозная headless проверка сравнивает JSON отчёты двух хостов, проверяет число экземпляров для квадратной и неполной сеток, а также ошибки входных параметров. Headless dummy renderer не сохраняет GPU transforms: проверка размещения последнего маркера выполняется только при запуске `--verify` с настоящим графическим backend. Тестовый фреймворк для этого этапа не нужен.

**Следующая граница.** Тики, команды, хранение изменяемого состояния, поток симуляции и рабочие задачи относятся к следующему этапу. Их проектирование начинается с численной модели и профилей нагрузки на 10000+ объектов. Постоянная стоимость на сущность, выделения памяти за тик, ожидание задач и масштаб карты рассматриваются до реализации массовых систем.
