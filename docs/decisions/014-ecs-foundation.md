# 014. Готовый ECS как основа состояния

Дата: 2026-11-05. **Принято пользователем; реализован первый перенос E0–E2.** [Проверки и замеры](../verification/015-ecs-production.md). [Исследование](../research/ecs-selection/README.md), [архитектура](../research/ecs-selection/architecture.md), [план](../research/ecs-selection/migration.md), [проверки API](../research/ecs-selection/probe/README.md).

## Решение

Использовать **Frent0.9.1-beta** на net10.0 для ECS хранения, запросов и компонентной композиции. Версия закреплена точно в Core, с package lock и уведомлением MIT. Реализованы baseline, ECS identity/lifecycle юнитов и production-пилот; остальные горячие данные пока в EntityState[].

Компоненты authoritative состояния — данные; игровые системы явно вызываются координатором SimulationWorld. Default Frent.World.Update и per-component EC callbacks не определяют игровой тик, порядок фаз, смерть или выпуск юнитов.

Actor означает игровую Entity с набором возможностей. Дополнительные superclass, огромный ActorComponent и ActorId не создаются. Existing OpenRTS EntityId сохраняется как стабильная внешняя идентичность; Frent handles с recycling остаются внутренними. Compiled immutable definitions отделяются от актуальных компонентов; Player при появлении его механики может быть непространственной entity.

Queries не выполняют игровые structural changes. Сначала формируют результаты, затем координатор применяет их за пределами enumeration в заданном доменном порядке. Смерти видны до production, каждый выпуск — следующему производителю. Automatic deferred buffer библиотеки не используется как FIFO gameplay journal. Ref на компонент не переживает structural commit.

Сохраняются fixed-point, fixed tick, собственный RNG, canonical hash/IDs, sequential oracle, job barriers и FrameExchange. Godot получает только опубликованные копии и события. Terrain, MotionIndex, общие навигационные caches и специализированный пул снарядов могут оставаться вне ECS.

Игровые реализации заменяются через composition root и конкретные контракты фаз/ресурсов. Core systems вправе использовать Frent напрямую; универсальный дубликат ECS API не создаётся. Замена игровой системы и замена ECS backend — разные по цене задачи.

## Причины и компромиссы

Frent поддерживает явные query-системы без обязательной EC модели поведения, разрешает постепенный перенос текущих состояний и не имеет runtime dependencies в выбранной net10 поставке. Проверены базовые APIs, internal handle invalidation, query-exit commit, пример канонического merge и запуск с Godot4.7.2.

Friflo3.6 технически подходит, но стандартный пакет тянет LGPL-3.0-only JSON dependencies; preview4 также. EasyEcs4.7 остаётся первым резервом; у него обязательная Nino RC dependency, быстрые изменения API и расхождение release/master. Лицензия восстановленного набора EasyEcs/Nino — MIT.

Frent сам остаётся beta. Этот риск принимается для пилота, с pinning и обязательной parity-проверкой до массового переноса. Исследование не доказало его превосходство по скорости над другими ECS. Источники, версии и фактические NuGet метаданные сохранены рядом с исследованием.

## Проверка решения

E0–E2: baseline существующих сценариев, lifecycle/ID integration и перенос Production. Gate — совпадение состояния/событий, соблюдение барьеров и сравнимые Release-профили. Перед E4 проверяются p95 Step, allocations и память на сопоставимых нагрузках. Существенные дефекты или необъяснённая регрессия требуют повторного выбора до массовой миграции; форк ECS заранее не планируется.

Первый перенос изменяет Core csproj и lifecycle потребителей, но сохраняет текущие production/navigation форматы. Рекомендация собственного промежуточного набора stores из прежнего Actor-исследования заменена готовым ECS, наблюдения о связности и границах ответственности сохраняются.


## Уточнение: игровой мир и хранилища

Frent.World рассматривается как хранилище. Одна игра может владеть несколькими независимыми Frent Worlds и обычными структурами данных; общий Tick, фазы, порядок межсистемных результатов и публикация принадлежат SimulationWorld. Нет требования помещать Players, Units и Projectiles в один ECS World или вообще использовать ECS для каждого домена.

Сейчас есть только unit storage: одна строка identity для каждого юнита/здания и ProducerState только у производителей. Игроки пока не реализованы; снаряды сохраняют существующий пул. Новые stores создаются по реальному потребителю, а не заранее. Межхранилищные ссылки используют доменные IDs; native handles не выходят к другим хранилищам или Godot. Разбиение не задаёт отдельные часы или независимый порядок игровой симуляции.

SimulationWorld теперь IDisposable. Прямой потребитель владеет его временем жизни; SimulationSession создаёт и освобождает мир на рабочем потоке до завершения Completion, в том числе при ошибке/отмене. Закреплённые кадры содержат копии и остаются валидными после освобождения ECS.
