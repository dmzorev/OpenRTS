# 008. Кадровая ходьба пехоты

Дата: 4 ноября 2026 года. Статус: реализовано.

Для первого набора используем классическую полную модель с четырьмя кадрами: левый шаг, нейтральная поза, правый шаг, нейтральная поза. Вариант с отдельными стопами пока не нужен. Он потребовал бы дополнительного слоя с собственным временем, направлением и точкой крепления, тогда как текущий SpriteFrames уже решает задачу.

У автоматчика и ракетчика отдельные атласы 2048×512, по четыре квадратных кадра. `travel` зациклен с частотой 8 кадров/с симуляции; `stand` и пока однокадровый `shoot` используют нейтральный кадр того же атласа. Исходные неподвижные PNG сохранены. Отдельное процедурное покачивание пехоты убрано: ноги уже нарисованы в разных положениях.

Одинаковый масштаб применяется ко всему циклу. После технической нормализации кадры совмещены по центру magenta-панели шлема, а не по нижнему краю ботинок: нижний край меняется при шаге. [Скрипт подготовки](../../tools/prepare_infantry_walk.py), [исходники, промпты и SHA-256](../assets/infantry-walk.json). Pillow нужен только для офлайн-подготовки; сборка/игра его не используют.

## Запуск и время

Существующий Core выбирает `move` по фактическому смещению за тик. Один приказ Move ещё не означает ходьбу: стоящий перед препятствием или прибывший юнит возвращается к `idle`. StartTick сохраняет фазу активного цикла. Адаптер выбирает SpriteFrames кадр по опубликованному тику и интерполяции; скорость игры и пауза уже действуют на это время. Дополнительного таймера реального времени нет.

Пакетная отрисовка сохраняется. Четыре региона одного атласа образуют четыре MultiMesh batch, поэтому у текущих пяти типов моделей 13 batch nodes вместо прежних 7. Количество узлов зависит от набора кадров, а не от числа сущностей. Это не оценка FPS: для значительно большего числа клипов стоит отдельно измерить вариант с UV на экземпляр.

## Дальнейшие эффекты Godot

Для ходьбы достаточно стандартного [SpriteFrames](https://docs.godotengine.org/en/stable/classes/class_spriteframes.html). Мы читаем этот ресурс своим пакетным адаптером вместо создания AnimatedSprite3D на каждого юнита.

Для будущих сложных графических дорожек подходит [AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html): он воспроизводит анимации свойств и позволяет задавать переходы. Для дыма подходит [GPUParticles3D](https://docs.godotengine.org/en/stable/classes/class_gpuparticles3d.html) с ParticleProcessMaterial; API допускает также явную эмиссию частиц. Это возможности Godot, а не новые обязанности Core.

Предлагаемый следующий шаг при реализации эффектов: отдельные точки крепления Model, короткие вспышки по независимым событиям и продолжительный дым по `damaged`. Частицы должны оставаться в мире после ухода машины. Ограниченный пул видимых эффектов/эмиттеров нужно проверять под нагрузкой; создание полного дерева AnimationPlayer/Particles для всех 10000 сущностей заранее не принимается. Сеть и пропуски графических кадров не должны терять игровые события.

В этой итерации дым и новые эффекты стрельбы не реализованы. У полного спрайта одна поза: существующий `fire` на той же части временно перекрывает ходьбу. Одновременные независимые ноги и стреляющий верх потребуют раздельных частей или комбинированных кадров. Наведение отдельно от движения допускает скольжение боком; обратная/боковая походка и привязка шага к пройденной дистанции остаются будущей графической работой.
