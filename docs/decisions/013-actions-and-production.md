# 013. Кастомные действия и очереди производства

Дата: 2026-11-05. Реализована первая версия способностей и производства без экономики. [Полигон и проверки](../verification/014-actions-and-production.md).

## Граница данных

`Actions.Buttons` — регистрация именованных действий в контенте. Из неё Content готовит две независимые части:

- Core: `AbilityDefinition` связывает ID с оружейным mount, разрешением наземной цели и начальным autocast; `ProductionDefinition` — с типом продукта, очередью и игровыми переопределениями.
- UI: `ActionButtonBinding` хранит название, иконку, хоткей и ID курсора. Это часть UnitCatalog.Presentations, исключённая из gameplay fingerprint. Симуляция не получает Button, Key, Cursor или Godot Resource.

Первый backend способностей использует имеющиеся WeaponDefinition/mount: подготовку, burst, cooldown, снаряд, splash, броню, отношения и ремонт. Набор именованных способностей можно расширять контентом. Произвольные скриптовые эффекты/бафы и пользовательский исполняемый код не вводятся заранее; для них понадобится реальный игровой эффект и его контракт воспроизводимости.

```yaml
rifleman:
  Armaments:
    Mounts:
      main: {Weapon: rifle}
      grenade: {Weapon: grenade}
  Actions:
    Buttons:
      grenade:
        Mount: grenade
        GroundTarget: true
        AutoCast: false
        Label: Граната
        Cursor: grenade
        # Hotkey: A     # переопределяет стандартное действие A
```

Именованная способность отключает обычное автоматическое использование связанного mount, пока autocast не включён. Простое наличие второго оружия не должно заставлять автоматчика тратить гранаты. У гранаты допустимы точка и вражеская цель; наземная точка фиксируется на запуске, попадание не гарантируется по движущейся цели. GroundTarget требует splash и не допускает repair/homing. Ремонт допускает только повреждённого союзника с ненулевым модификатором брони.

## Ручное и автоматическое применение

`UseAbility` получает Action ID, immutable recipients, точку и/или EntityId цели. Существующие получатели обходятся по ID. Выбирается **один** с таким действием, допустимой целью, закончившимся cooldown и без уже выполняемой ручной способности/подготовки. Он при необходимости сближается, выполняет обычный оружейный windup и одну серию. Кулдаун принадлежит mount и не сбрасывается новым приказом или переключением autocast. Новый Move/Stop отменяет ещё не выпущенную атаку через прежнюю систему приказов; уже выпущенный снаряд остаётся.

При отсутствии исполнителя команда отклоняется с ActionUnavailable. Ручной ремонт в новой схеме — одно применение; следующий приказ может выбрать другого готового инженера. Автоматический ремонт продолжает искать допустимых союзников в пределах range. Прежний RepairTarget остаётся программным совместимым приказом длительного ремонта; стандартная кнопка/E убраны из стенда, контекстный ПКМ направляется в зарегистрированную способность.

`SetAutoCast` задаёт bool для каждого получателя; это игровой параметр, он хешируется и публикуется в WeaponPose вместе с ReadyTick/Busy. Он не зависит от текущей панели или UI FPS. Переключение кнопкой над смешанной группой включает режим всем, если не все уже включены; иначе выключает всем. Auto сохраняет правила движения конкретного mount, фильтры целей, acquisition и reload.

## Панель и выбор подгруппы

В стенде типы выбранных объектов показываются иконкой и количеством. Типы с кастомными действиями идут первыми, затем стабильная сортировка по Unit ID. Tab/Shift+Tab и клик переключают активный тип, сохраняя полный выбор. Панель и получатели кастомной кнопки относятся к активному типу. Стандартные групповые приказы продолжают относиться к полной подходящей выборке.

Первые шесть кнопок получают Q/W/E/R/T/Y в порядке Order, затем ID; Hotkey переопределяет назначение. Кастомный хоткей проверяется **до** стандартного действия и редакторских клавиш. UI показывает состояние autocast, минимальный оставшийся cooldown среди выбранных исполнителей и полоску перезарядки. Переход выбора обновляет панель сразу, до следующего графического кадра. Перестроение типа происходит по revision выбора; состояние кнопок — по simulation tick или локальному изменению режима.

`RtsOverlay.RegisterCursor` регистрирует ID с цветным индикатором либо анимированным SpriteFrames, sequence и hotspot. Binding выбирает его по ID. В прототипе grenade/repair имеют процедурные индикаторы; сетевые/AI команды от них независимы. Правый клик по способности переключает autocast, левый/хоткей включает наведение. Esc/ПКМ отменяют наведение.

## Строительные параметры и очереди

```yaml
rifleman:
  Buildable: {Ticks: 75, Cost: 100, Kind: Unit}

power-plant:
  Buildable: {Ticks: 125, Cost: 500, Kind: PlaceBuilding, PlacementRadius: 102400}

barracks:
  TaskQueues:
    Queues:
      infantry:
        Capacity: 20
        Payment: Upfront
        Exit: [0, 1024]
        ExitSearchRadius: 2048
        WorkingState: working
        ExitAnimation: door
        ExitAnimationTicks: 40
  Actions:
    Buttons:
      rifleman: {Unit: rifleman}  # остальное берётся из Buildable
      rocketeer: {Unit: rocketeer, Cost: 90, Ticks: 100}
```

У производителя до восьми именованных очередей, у каждой свой Capacity (1..256), Payment, выход/радиус поиска и необязательные семантические WorkingState/ExitAnimation. Действие выбирает Queue либо первую по ID. Цена, Ticks и PlacementRadius могут переопределяться у действия производителя. Unit/PlaceBuilding берётся из Buildable продукта. Цель должна существовать и быть buildable; PlaceBuilding требует footprint, обычный Unit не может скрыто устанавливать footprint.

`Cost` — неотрицательный демонстрационный скаляр. Upfront/Progressive/OnCompletion сейчас **только политика в определениях**: баланса, списаний и возвратов нет. Player actor, ресурсы, проверка доступности цены и остановка по недостатку средств появятся вместе с экономикой. Не следует интерпретировать отображаемую цену как произведённое списание.

Каждая очередь — FIFO задач с устойчивым глобальным TaskId, Product index, Progress, Ready, Repeat и признаком блокирования выхода. Прогресс увеличивается на один на тике, включая тик принятия заказа; задача Ticks=1 готова в конце этого тика. Все именованные очереди работают параллельно, следующий элемент одной очереди начинается на следующем тике после завершения/снятия предыдущего. Готовое здание/занятый выход удерживают голову.

`EnqueueTask` распределяет каждый элемент пакета по **наименьшей длине подходящей очереди**, при равенстве по EntityId. Полные очереди исключаются. Если общий лимит исчерпан, уже принятые элементы остаются; остаток отклоняется. UI посылает1 или5, API допускает1..256 за команду. Длина учитывает активный и готовый элементы, а не остаток времени.

Правый клик добавляет повторяемую задачу; после фактического выпуска или размещения она переносится в хвост с новым TaskId и нулевым Progress. Несколько повторяемых задач чередуются. Shift+ПКМ добавляет5 повторяемых задач, а не один заказ на пять мгновенных результатов.

В UI задачи активного типа агрегируются по Queue/Action/Repeat сразу по выбранным производителям. Обычные и повторяемые элементы имеют разные стопки. Иконка показывает количество, ∞, готовность и прогресс; tooltip содержит тип и очередь. ЛКМ отменяет1, Shift+ЛКМ —5, ПКМ — всю стопку. `CancelTasks` снимает **новейшие подходящие TaskId**, сохраняя уже накопленный прогресс головы, пока есть ожидающие элементы. Порядок FIFO каждого производителя не меняется от группировки интерфейса.

## Выпуск, rally и размещение

Производство исполняется после движения и боя: умерший производитель не выпускает последний продукт в тот же тик. Данные хранятся только для производителей, обход — по устойчивым ID. Spawn нового производителя не добавляет его в текущий обход до следующего тика.

Обычный юнит появляется у заданного Exit относительно центра производителя. Ограниченная решётка256 ищет ближайшую допустимую остановку в ExitSearchRadius с учётом всего тела, terrain и занятости. Если выхода нет, готовая задача остаётся и повторяет попытку; бесконечного накопления юнитов в одной точке нет. Глобально допускается до32 выпусков за тик; прочие готовые задачи ждут. Это ограниченный прототип поиска выхода, без гарантий пропускной способности фабрик.

Работающая голова добавляет настроенный WorkingState к опубликованному представлению; ручные состояния при этом не стираются. После выпуска проигрывается настроенный ExitAnimation на дорожке Body — дверной слой остаётся независим от оружейных анимаций ремонта. Дверь визуальная; её анимация не определяет физическую проходимость двора.

SetRally либо обычный Move по неподвижному производителю задают точную точку выхода. Она публикуется в EntityPose и рисуется флагом. Готовый юнит получает обычный Move к ней; недоступный terrain корректируется прежним resolver. После смешанного приказа здания получают rally, мобильные участники продолжают групповое движение. Стационарные объекты без очередей остаются неподвижными и не получают rally.

В стиле C&C готовый PlaceBuilding остаётся задачей до явного `PlaceProduced(TaskId, Action, Producer, Position)`. ЛКМ по готовой кнопке включает прежний preview размещения. Core проверяет тип, готовность, range между границами, alignment, bounds и конфликт с телами; только успешный Spawn расходует задачу. Невалидная точка, повтор команды или устаревший TaskId не создают дубликаты и не теряют продукт. Цена уже готового здания повторно не пересчитывается; определения неизменяемы. Уничтожение производителя снимает и готовые, и ожидающие задачи.

## Программный вход

Кнопка и код клиента используют одни команды. Для способности доступен также прежний фасад UnitAction:

```csharp
session.Issue(new(UnitActionKind.Ability, new EntitySet(ids), point, Action: "grenade"));
session.Submit(CommandKind.SetAutoCast, recipients: new EntitySet(ids), action: "grenade", enabled: true);
session.Submit(CommandKind.EnqueueTask, recipients: new EntitySet(producers), action: "tank", amount: 5, repeat: true);
```

Прямой headless клиент передаёт соответствующие WorldCommand в Step. AI не нажимает UI кнопки. Action ID проверяется по определениям получателя, TaskId размещения проверяется по готовой очереди. Авторизация владельцев/полноценная дипломатия остаются прежней границей хоста, без нового сетевого протокола.

## Кадры и состояние

FrameExchange публикует flat TaskPose вместе с EntityPose/WeaponPose/ProjectilePose в том же lease. Task spans запрещено использовать после Dispose. События TaskAdded/Cancelled, ProductionReady/Blocked, Produced передаются отдельно от пропускаемых графических кадров. Состояние и повтор команд сравниваются в прямом, threaded и Godot хостах.

Форматы: **direct7 / navigation11 / UnitCatalog fingerprint7**. Хеш включает очереди, TaskId cursor, ready/progress/repeat, rally, autocast и активную способность. UI выбор подтипа, хоткей, изображение и курсор исключены. Исторические отчёты прежних этапов не переписываются.
