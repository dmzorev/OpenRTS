# Приоритеты и реализация сетевого слоя

**Статус на17ноября2026:** реализованы NET0, headless NET1, NET2 LAN/UI и WAN pipeline, NET3 lifecycle, NET4.1–4.3 и первый сервис NET5 — в пределах контрактов037–044 и проверок ниже. NET6–NET9 остаются будущими этапами. Аудит NET1–NET5 выявил восемь доработок; пункты1–8 исправлены. Каталог/вместимость/диагностика и воспроизводимый native стенд — [контракт046](../../decisions/046-network-directory-diagnostics.md), [проверки046](../../verification/046-network-directory-diagnostics.md). [Контракт исправлений045](../../decisions/045-network-audit-hardening.md), [проверки045](../../verification/045-network-audit.md). Физический LAN/WAN, разные ОС/CPU и публичный HTTPS deployment ещё не подтверждены; процессные UI/realtime и WAN impairment проверены на одной машине. [Алгоритмы](design.md) · [референсы](references.md) · [контекст](README.md).

Приоритеты: **P0** — без этого нельзя выпускать соответствующий режим; **P1** — следующий полезный результат; **P2** — дополнительные возможности после измерений. Защищённый режим — последняя дополнительная возможность, не критерий готовности основной сетевой игры. Этапы не являются оценками календарных сроков.

## Доработки после аудита NET1–NET5

Нумерация соответствует отчёту аудита; закрытие найденных ошибок не означает завершения всего первоначального backlog.

| P1 / 7 | В текущем UI нет Waiting/RTT | Исправлено: Waiting с тиком/ID/временем и RTT по nonce Ping/Pong; таймауты обязательных команд не продлеваются |
| P1 / 8 | Godot NET3 может поставить паузу раньше готовности проверок других окон | Исправлено: barrier меню и ожидаемый spectator до Start; пройден native сценарий с задержкой UI1800мс |

Следующий приоритет — отдельное восстановление зелёного Gameplay baseline (восемь известных ошибок: repair, пять ECS traces, skirmish economy, supply). До внешних обещаний поддержки выполнить физический LAN/WAN, cross-platform determinism, fuzz decoder и измерения больших матчей/snapshots. Затем продолжать NET6.

Явно остаются в backlog: surrender с игровым поражением, динамическая дипломатия/shared vision; автоматический NAT traversal, самостоятельный relay и мониторинг; observer catch-up без паузы, индекс runtime checkpoints для seek, сохранение AI policy и host recovery/migration. Настроенный TCP relay и восстановление клиента не закрывают эти возможности. Trusted mode остаётся последним optional NET8/NET9.

## Основное направление (уточнено пользователем 16 ноября 2026)

По умолчанию матч использует клиентский lockstep, близкий к OpenRA/0 A.D./Recoil: клиенты напрямую обмениваются командами и каждый рассчитывает полный мир. Клиент-хост может координировать участников; это не обязательный отдельный сервер. Игра по IP, её завершение, replay, зрители и восстановление не должны требовать доступности внешнего сервиса.

Необязательный сервер прежде всего помогает искать игры. Он также может подключаться как зритель: получать историю команд, воспроизводить матч, собирать статистику, анализировать партии и баланс, искать признаки читерства. Он не назначает игровые результаты и не входит в барьер готовности игроков. Отказ/отставание аналитики не останавливают матч. Сбор данных явно настраивается для матча; без сервера сохраняется обычная игра и локальный журнал.

Безопасный режим с доверенным (удостоверяющим) сервером — отдельная опция **при создании игры**, выключенная по умолчанию. В ней сервер рассчитывает истину и фильтрует сведения. Разрабатываем её в последнюю очередь, после полноценной основной клиентской версии и необязательных сервисов. Аналитическое обнаружение подозрительного поведения в обычном режиме не равно предотвращению map-hack.

Нумерация будущих этапов пересмотрена: прежние NET6/NET7 доверенного сервера перенесены в NET8/NET9; NET6 теперь сервер-зритель и аналитика, NET7 — дополнительные возможности основной версии. Реализованные NET0/NET1 и ближайшие NET2–NET5 сохраняют номера.

NET5/NET6 — дополнительные сервисы, не зависимости прямого подключения. Сервер-зритель подключается после готовности игроков, догоняет по журналу и не добавляется в их tick barrier. Обычные зрители/replay и аналитика не ждут реализации NET8/NET9. Гарантированная задержка omniscient-выдачи недоверенному зрителю требует отдельной policy: полный live lockstep поток нельзя скрыть задержкой UI.

## NET0 — основа (выполнен в этой работе)

Созданы `src/OpenRTS.Network/OpenRTS.Network.csproj` и README, подключение в `OpenRTS.sln`, направление Network→Gameplay→Core. Без транспорта, классов-заглушек, запуска сети и новых пакетов. Исследование, проект и roadmap связаны с общей архитектурой. Успешная сборка каркаса не доказывает сетевую корректность.

## NET1 — минимальный прямой матч (реализован headless-срез)

**Гипотеза:** текущих fixed Step, canonical command ordering и программного создания мира достаточно для двух синхронных клиентов без изменения игровых правил.

**Объём:** TCP loopback/LAN,2peers, фиксированный match descriptor и delay, ограниченный whitelist обычных RTS приказов, честная identity player1/2, barrier, stop-on-disconnect/desync. Минимальный отдельный исполняемый Network test harness добавить при появлении логики; зарегистрировать в `tools/dev.sh test`. UI и подключение из интернета ещё не критерии NET1.

**Проверки:** одинаковый seed/сценарий и журнал дают одинаковый hash на каждом контрольном тике у двух процессов и offline replay; разный FPS/worker count не влияет. Прогнать пустые тики, simultaneous commands, большие EntitySet, split/coalesced TCP reads, дубли, конфликтующий дубль, future/past tick, пропуск sequence, неверные версии/карта/seed, запрещённый issuer0 и команды чужим объектам. На сетевой паузе Tick не меняется, Dispose не ждёт отсутствующего пакета бесконечно.

**Готово, когда:** автоматический процессный сценарий и LAN запуск воспроизводимы, все входные buffers ограничены, mismatch останавливает матч с журналом. Начальный whitelist может не покрывать все способности; UI следующего этапа не предлагает неподдержанные приказы. При расхождении прежде локализовать игровой determinism/codec; state sync не используется для маскировки ошибки.

## NET2 — игра для двух людей и проверка WAN (реализован в проверенном профиле)

**Результат:** pipeline закрывает команды D тиков вперёд, reader/writer независимы от Step, hashes периодические с bounded verification lag. Пройдены model-профили RTT0/50/150/300, jitter до80мс, loss1/5%, медленный расчёт/read и ограниченная полоса; реальные kernel netem drops проверены под TLS. Каждый прогон совпадает у peers и с replay; для фиксированного model-журнала также проверен независимый offline runner. Численные результаты и пределы — [039](../../verification/039-net2-wan.md). TCP/TLS сохранён: корректность подтверждена, head-of-line задержки отражены в latency tails. Смена транспорта пока не обоснована этим малым профилем. Следующий этап NET3 реализован в [040](../../decisions/040-net3-multiplayer-lifecycle.md).

**Гипотеза:** фиксированного input delay достаточно для выбранного RTT профиля; TCP head-of-line пока приемлем.

**Объём:** Godot host/join IP/port, ready/start, отображение connection/wait/ping, разрешённые команды skirmish, корректный выход и локальные меню. Общий pause/скорость требуют протокольного решения; текущие offline playback controls не дают менять скорость одного участника. Обеспечить TLS identity, лимиты/дедлайны handshake и журналов до внешних тестов.

**Проверки:** два приложения на разных машинах, подключение/неверный адрес/таймаут/закрытие во время ожидания; policy владельцев, transform/transport/production и stale target; fuzz decoder без world mutation. Профили стенда: RTT0/50/150/300мс, jitter0/20/80мс, потери0/1/5%, краткий разрыв и slow consumer. Это тестовые точки, не обещание играбельности при300мс/5%.

**Критерий:** пользователь может завершить тестовый skirmish, задержка input→apply измерена, ресурсы ограничены. По p95/p99 stall и командам определить допустимые delay/RTT. При плохом результате сравнить увеличение D и готовый transport с независимыми каналами; не писать custom reliability до сравнения.

## NET3 — несколько игроков и жизненный цикл

**Результат:** StarSession на2–8сторон (sandbox до4), pinned TLS, лобби с revision-bound Ready/Start, согласованные pause/leave/drop, AI assignment/takeover на хосте и bounded чат. Журналы оставшихся совпадают побайтно и воспроизводятся; проверены8human, асимметричный WAN, потеря хоста и3процесса Godot + AI. [Контракт040](../../decisions/040-net3-multiplayer-lifecycle.md), [проверки](../../verification/040-net3.md). Вход посреди игры зависит от NET4. В [041](../../decisions/041-game-shell-and-lobby.md) добавлены передача настроек от Host, закрытые места, фиксированные команды, LAN-каталог и зрители с начала. Полная дипломатия в ходе матча, shared vision и surrender как игровое поражение остаются отдельным продолжением.

**Объём:** host-star, lobby slots/teams, смена настроек с отменой Ready, game phase, agreed pause/drop/surrender и AI input policy. Отдельный Chat канал не участвует в simulation hash; текст/частота ограничены. Сначала потеря хоста завершает матч, автоматического host migration нет.

**Критерий:** одинаковый journal/control history у всех при позднем вводе, отключении, одновременном ready/config change. Проверить асимметричный разрыв: только хост принимает membership-решение; оторванный клиент не начинает самостоятельную подтверждённую ветвь. При неспособности сохранить agreement завершать матч явно.

## NET4 — сохранение, восстановление, replay и первые зрители

**Текущий статус:** NET4.1 реализован: журналv3 с bootstrap, replay UI/POV/seek и bounded ReplayCheckpoint с восстановлением от0. [Контракт042](../../decisions/042-net4-replay-recovery.md), [проверки](../../verification/042-net4.md), [разбиение NET4.1–4.3](net4.md). ReplayCheckpoint остаётся историей O(K). NET4.2 добавляет runtime snapshot со схемами состояния, NET4.3 — token/epoch, chunks, возврат двух участников и позднего зрителя на общей паузе; [контракт043](../../decisions/043-net4-runtime-snapshot-rejoin.md), [проверки](../../verification/043-net4-runtime-rejoin.md). Непрерывный observer catch-up и индекс checkpoints для replay seek остаются продолжением.

**Гипотеза:** полный canonical checkpoint позволяет продолжить симуляцию без изменения дальнейшего hash. Это отдельная значимая работа над Gameplay/Core, не сериализация ECS памяти.

**Объём:** версионированный snapshot/restore и журнал, restart test, reconnect tokens/epochs, bounded transfer и catch-up. Сначала replay от0 и зритель с начала матча; mid-game join/checkpoint seeking после доказательства restore. Lockstep spectators получают полный мир и не относятся к защищённому соревновательному режиму.

**Критерий:** save на тикеK, restore и доигрывание доT совпадают с непрерывным запуском на каждом дальнейшем checkpoint. Покрыть RNG, выданные IDs, burst/windup, очереди с progressive payments, partial flight/boarding, navigation local path/yield, construction и сенсорные знания. Проверить недокачанный/повреждённый snapshot, долгий catch-up и два одновременных rejoin. Если равенство нарушено, exact restore считается незавершённым; оставить replay от0 с лимитом длительности.

## NET5 — поиск матча и допуск

В обычном матче хост принимает запрос сразу по TLS, проверяет пароль и атомарно выдаёт фактическое место. Один матч может быть опубликован на нескольких узлах. Гость получает адрес и отпечаток из выбранной записи и может войти после отключения каталога. StarProtocol 6 требует обновления хоста, гостей и самостоятельного каталога. Первоначальная схема NET5 с отдельным issuer доступна через явно заданный admissionPolicy. [Сценарии и порты](../../../src/OpenRTS.Network/README.md#net5-поиск-матча-и-допуск)

Клиент использует список игр, одно адресное поле и поиск LAN. Все зарегистрированные матчи опубликованы. Пароль запрашивается только при входе в закрытую паролем комнату. Адреса по умолчанию и необязательный адрес публикации задаются в [network.yaml](../../../sandbox/network.yaml). Копии объявлений имеют ограниченный срок. Задача физической проверки остаётся открытой для двух компьютеров, включая Wi-Fi с блокировкой broadcast и ручной ввод адреса при разрешённых входящих TCP-соединениях.

В OpenRA LAN-объявления и результаты удалённого поиска объединены в одном списке. Steamworks описывает разрешение конфликтов владельцем лобби и дальнейшее соединение участников с игровым хостом. В OpenRTS владелец лобби и игровой хост совпадают. [OpenRA ServerListLogic](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Widgets/Logic/ServerListLogic.cs) · [Steamworks Matchmaking & Lobbies](https://partner.steamgames.com/doc/features/multiplayer/matchmaking)

**Проверки:** stale lobby/heartbeat, двойной ticket, ticket другой роли/матча, истёкший credential, недоступный endpoint и NAT fallback, rate limits. Credentials в логах отсутствуют. UPnP/port mapping не включать незаметно; выбранный NAT механизм и relay provider требуют отдельного решения по зависимости/эксплуатации.

**Критерий:** игрок находит совместимый матч, получает проверяемую роль и либо подключается, либо видит конкретную сетевую ошибку. Matchmaker/rating и массовая инфраструктура отложены до реального спроса. Relay не называется защитой от map-hack.

## NET6 — необязательный сервер-зритель и аналитика

**Объём:** подписка на поток команд/контрольных hashes и/или загрузка завершённых replay, воспроизведение полных матчей сервером-наблюдателем, версионированные метрики по исходам, экономике, производству, боям и использованию контента. На этой основе — анализ партий, предложения по балансу и поиск подозрительного поведения. Сервер не исполняет роль авторитета матча и не присылает коррекции мира клиентам.

**Контракт:** вне игрового barrier, собственные bounded очереди/история/квоты и catch-up. Медленный сборщик теряет подписку или продолжает по архиву, а не тормозит игроков. У каждого набора данных есть match/build/content identity, источник, полнота и результаты сверки hashes. Политика публикации полного replay/доступа к live данным согласуется при создании матча, чтобы аналитический endpoint не открывал сведения сопернику.

**Проверки:** сервер отсутствует до старта, отключается в бою, отстаёт, присылает неподходящую версию; игроки всё равно завершают матч. Проверить частичный/подделанный replay, разные отчёты игроков и повторную загрузку без двойного учёта статистики. Сервер может проверить воспроизводимость полученной записи, но не гарантировать отсутствие map-hack/сговора. Автоматические санкции и изменение баланса не следуют из одного подозрения; сначала формируются проверяемые отчёты.

**Критерий:** обычный матч полностью работоспособен без сервиса; подключённый наблюдатель даёт воспроизводимые метрики, не меняя результат и задержки продвижения игроков.

## NET7 — дополнительные возможности основной клиентской версии

Player/team/omniscient POV, spectator join, replay UI/экспорт, broadcast, moderation hooks; затем по реальным требованиям — подбор/рейтинг, турниры, host migration и устойчивость необязательных сервисов. Базовые зрители уже появляются в NET4. Готовность этих функций не зависит от защищённого сервера.

**Критерии:** зритель не задерживает игроков, история и bandwidth ограничены, смена роли и доступ к полному replay соответствуют policy матча. Проверить потерю клиента-хоста и исключить две одновременно подтверждённые ветви при migration. В обычном lockstep нельзя обещать защиту от передачи зрителем текущей скрытой информации игроку; требования к надёжно задержанному потоку отдельно реализуются в NET9.

## NET8 — последний дополнительный режим: доверенный сервер

**Приоритет:** только после основной клиентской версии и её дополнительных возможностей. Опция при создании игры, по умолчанию выключена; выбранный режим фиксируется в descriptor/handshake до раскрытия мира. Это не обязательный переход всех матчей на сервер.

**Гипотеза:** серверная стоимость полной симуляции и фильтрованной выдачи приемлема в выбранном профиле. **Объём:** отдельный headless процесс, серверное назначение команд/времени, полная серверная симуляция, knowledge DTO и клиентский read model без скрытого мира. Сначала надёжные keyframes на малом сценарии; delta и масштаб — NET9.

**Проверки:** разные режимы отвергают несовместимое подключение; обычный матч по-прежнему запускается без сервера. Поддельные HP/позиции/owner/admin не меняют истину защищённого матча. Два серверных мира с одинаковыми разрешёнными знаниями дают одинаковый нормализованный исходящий поток, несмотря на различия скрытых армий. Проверить initial map/seed, footprint, projectiles/events, radar, Previous, economy и ссылки DTO.

**Критерий:** завершён маленький защищённый матч и сохранена самостоятельность обычного режима. Дорогие фазы оптимизировать на сервере; передача скрытой истины клиенту не считается успешной защитой.

## NET9 — завершение защищённого режима

Versioned keyframe/delta, ACK baselines, permission-first prioritization, надёжные lifecycle/events, backpressure, защищённый rejoin, security review и тесты утечек. Затем серверная задержка зрителей, durable checkpoint/journal, crash recovery и проверяемые результаты. Полный save NET4 нужен для server recovery; клиентский protected rejoin получает только новый filtered keyframe.

**Критерий:** потери/reorder/slow consumer не раскрывают уже скрытые поля и не дублируют события; задержанные данные удерживаются сервером, а не только UI. Восстановление сохраняет idempotency платежей/задач и объявленную границу подтверждений. Бюджеты CPU/uplink/memory и RPO/RTO устанавливаются измерениями для конкретных профилей. Возможности NET8/NET9 не становятся обязательными для обычной игры.
