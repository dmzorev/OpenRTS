# Удержание видимости и повторное использование зон колонной

9 ноября 2026. **Статус:** эксперимент, не новый режим по умолчанию. [Результаты и условия замеров](../../verification/035-fog-retention.md). Основа — собственная реализация F1 и [групповой кэш](group-optimization.md), без переноса чужого кода.

## Вопрос и предварительный вывод

Проверяем, может ли зона оставаться видимой ещё2–50 тиков после ухода наблюдателя, чтобы обзор визуально затухал и следующий юнит мог использовать прежнее покрытие. Сравнение показало два разных эффекта. Удержание по клеткам имеет небольшую стоимость, но само по себе не сокращает вычисление кругов. Кэш геометрических зон действительно повторно используется колонной, однако выгоден только при подходящем маршруте/интервале следования и заметно увеличивает память. Универсально включать такой кэш не следует.

Тестируем длительности0,2,5,12,25,50 тиков при25Гц: 0,0.08,0.2,0.48,1,2секунды. В игровой эксперимент можно передать любое целое0..250; длительность задаётся тиками, не реальным временем. Пауза останавливает игровое удержание. Основной матч по умолчанию сохраняет0.

## Что именно удерживается

Это *реальная видимость области*, а не призрак объекта и не только исчезающий визуальный след. Пока удерживается клетка, игрок получает текущее состояние объектов в ней, включая вновь вошедшего противника; бой может выбирать такие цели. После смерти наблюдателя зона также держится до срока. Такой игровой эффект требует отдельного выбора владельцем игры перед включением по умолчанию.

Таймер имеет исключительную верхнюю границу. При потере текущего покрытия на тике`t` и длительности`H` клетка видима на`t..t+H-1`, на`t+H` становится разведанной. Возвращение обзора отменяет старое истечение; последующий уход задаёт новый срок. При пакетном обмене источниками временное1→0→1 не создаёт нового таймера.

Чисто визуальное затухание можно использовать отдельно от этой игровой политики: оно не ускоряет authoritative fog, поскольку тот должен продолжать обновляться без задержки. В текущем эксперименте декоративный круговой след использует тот же H, но не передаёт результаты обратно в симуляцию.

## Вариант A: таймер клетки

Реализован opt-in через `GameplayMechanics.FogVisibilityHoldTicks`.

1. Текущие покрытия кругов и групп обновляются прежним алгоритмом. Для первой записи в затронутую клетку запоминается, было ли текущее покрытие положительным до пакета.
2. В конце пакета при положительном покрытии срок очищается. При переходе положительного покрытия в нулевое устанавливается`visibleUntil = tick + H`. Если покрытия не было до/после пакета, уже запущенный срок не продлевается.
3. Запрос возвращает Visible, если есть текущее покрытие **или** `visibleUntil > tick`. Старые сроки можно хранить до перезаписи: истёкший срок игнорируется, обход очереди таймеров не нужен.
4. Часы fog обновляются до проверки неизменности sources. Поэтому таймер истекает даже когда все наблюдатели стоят или исчезли. Это важно: прежний пропуск одинаковых descriptors не должен замораживать таймеры.
5. История карты, длительность и ещё действующие сроки входят в state hash. Истёкшие сроки сериализуются как0; derived contributors по-прежнему не хешируются. Полное save/load не реализуется этим изменением.

Дополнительные поля на клетку: Int64 срока и bool старого покрытия; в Explored также требуется dirty-маска. Суммарный бюджет полей валидируется до выделения памяти по реальному набору массивов. При H=0 этих массивов нет, старый hash-формат сохранён.

## Вариант B: кэш точных геометрических зон

Изолированный prototype внутри headless-бенчмарка; не подключён как backend основной игры.

Ключ зоны — Owner/X/Y/Radius в точных world coordinates. ID наблюдателя в ключ не входит: любой следующий юнит того же владельца может занять ту же геометрическую зону. Пока зону занимает хотя бы один наблюдатель, её вклад активен. После ухода последнего назначается истечение черезH. При возвращении до удаления запись и её вклад сохраняются. При наступлении срока запись снимается, если она не была обновлена. Устаревшие элементы очереди истечения проверяются по актуальному сроку и не удаляют переиспользованную запись.

Все активные и удерживаемые зоны подаются в обычный FogOfWar как неподвижные contributors с синтетическими ID. Следующая особь колонны может повторно использовать старые зоны, но число хранимых зон и цена их обхода увеличиваются. В prototype есть лимит1Mi записей и проверка исчерпания ID; это не production-политика деградации. Возвращение новой зоны на тике удаления обрабатывается до снятия: промежуточный разрыв покрытия не публикуется.

Оба варианта дают одинаковую дискретную видимость для одинакового H. Самопроверка сравнивает все клетки после каждого тика на случайных сценариях; каждый измеренный A/B также сравнивает итоговый digest карты. Производительность H=0 и H>0 нельзя оценивать по совпадению мирового hash между ними: изменение длительности намеренно меняет игру.

Ожидаемый интервал повторения зоны задаётся шагом между юнитами и их скоростью. Для pitch1024/step128 это около8 тиков. В измерении H=5 ещё не даёт повторного использования, H=12 уже даёт. При pitch256 шаг повторения около2 тиков; проверен и этот случай. Точное совпадение позиций, профиля и владельца обязательно; близкое прохождение само по себе cache-hit не даёт.

## Затухание в Godot

Для точной сетки кадр публикует byte-яркость: текущее покрытие255, удерживаемое пропорционально оставшимся тикам, истёкшее0. Это immutable данные того же слота/viewer, отдельные от статуса цели. Публикация добавляет проход по клеткам и копирование; замер ядра fog не включает эту стоимость.

Для красивых кругов используется декоративная история маски в двух ping-pong viewport. На обновлении отображаемого тика берётся максимум текущих кругов и прошлой маски, уменьшенной на прошедшее число тиков/(H+1). Она рисуется внутри уже разведанных квадратов и используется также на minimap. Смена viewer, перезапуск/обратный tick и смена H сбрасывают декоративную историю, чтобы она не переходила между игроками. При пропусках кадров применяется фактически прошедшее число тиков; невидимые рендеру промежуточные круги не восстанавливаются. Поэтому декоративный след может отличаться от authoritative клеточного удержания; отображение объектов продолжает использовать только последнее.

Два дополнительных viewport создаются лениво только при положительном H. Для H=0 прежний визуальный путь не получает этих ресурсов. GPU-стоимость их проходов и больших масс кругов отдельно не измерялась. Вариант только с яркостью клеток сначала давал тёмные швы у границы текущего круга; визуальная история маски устраняет эту проблему без изменения игровой геометрии.

## Выбор после эксперимента

- Для визуальной оценки разумно начать с5–12 тиков, выбирая ощущение игры. Не обосновывать выбор эстетической длительности выигрышем, которого нет на прямой колонне.
- Для геометрического кэша есть подтверждённый выигрыш на повторяющемся зигзагообразном пути при12тиках;25–50 тиков почти не улучшают скорость и увеличивают память.
- На прямой колонне текущий фазовый кэш групп существенно быстрее временного memo. На расходящихся траекториях memo хуже по времени и памяти. Поэтому его нельзя заменить им безусловно.
- Если этот backend понадобится, следующий этап — адаптивный выбор по фактическому reuse и памяти, пул записей/буферов и полный замер World.Step + кадры + GPU. Прежде чем делать это, решить, нужна ли игре сама задержка раскрытия/потери целей.

Запуск: `./tools/dev.sh run --fog --fog-hold=12`. Для основной игры флаг также передаётся в выбранный матч. Сравнение: `./tools/dev.sh benchmark --fog-retention-benchmark --count=10000 --ticks=80`.
