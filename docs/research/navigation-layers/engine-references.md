# Разделение навигации и движения в RTS: проверенные референсы

4 ноября 2026 года. Цель — уточнить слои для OpenRTS: достижимость по рельефу, маршрут, возможности движения, точная геометрия и временные препятствия. Это целевое чтение исходников трёх движков, а не сравнительный бенчмарк. Референсные игры не запускались; код не переносился в MIT ядро. Версии, прочитанные функции и ограничения доступа перечислены в [реестре источников](sources-engine.md).

## Основной вывод

Условие «есть путь», стоимость выбранного пути, допустимость остановки и физическая возможность исполнить следующий шаг — разные ответы. Общая карта может быть клеточной, тогда как позиции и короткие отрезки движения остаются точными. Постоянная привязка позиции юнита к центру клетки для этого не требуется. При этом любое сглаживание маршрута должно проверять весь пройденный отрезок с размером юнита: свободной конечной точки недостаточно.

Это инженерный вывод из сочетания следующих реализаций, а не утверждение, что какой-либо референс полностью удовлетворяет требованиям OpenRTS.

## OpenRA: профиль движения и политика блокирования

**Наблюдения.** `Locomotor` связывает тип грунта с двумя отдельными значениями: фактической скоростью и стоимостью поиска. По умолчанию стоимость обратна скорости, но `PathingCost` может её переопределить. Неуказанный тип грунта непроходим. Здесь же отдельно проверяются движение через клетку, возможность оставаться в ней, союзные подвижные блокировщики, уничтожаемые препятствия, временные проходы и свободные subcells для мелких юнитов. Это несколько независимых правил, а не одно перечисление состояний клетки. [N001: Locomotor](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/World/Locomotor.cs#L61).

`PathFinder` держит варианты иерархических данных по профилю движения: только рельеф и рельеф с частью неподвижных объектов. Отдельный запрос теоретической достижимости не учитывает юнитов. Проверка с неподвижными объектами прямо допускает положительный ответ, который потребует дальнейшей проверки. Источник и цель могут быть несимметричны: выход из уже занятой непроходимой области допускается, вход туда — нет. [N002: PathFinder](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/World/PathFinder.cs#L251).

Для близкой цели `HierarchicalPathFinder` сначала пробует ограниченный локальный поиск с обычным весом эвристики; дальний использует абстрактный граф связных областей. Этот граф направляет подробный поиск. Реализация различает то, что знает абстракция о рельефе/неподвижных объектах, и дополнительные мобильные препятствия конкретного запроса. Наличие иерархии само по себе не гарантирует оптимальность с любыми весами эвристики. [N003: близкий поиск](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Pathfinder/HierarchicalPathFinder.cs#L835).

В `Move` локальная блокировка запускает ожидание, уведомление блокировщика и повторный поиск с разной строгостью учёта акторов. Физическая непроходимость сейчас не означает окончательный отказ от дальней цели. Это полезный пример поведения поверх поискового алгоритма. [N004: обработка блокировщика](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Activities/Move/Move.cs#L250).

**Ограничения.** `MoveIntoShroud` разрешает или запрещает приказ в неизведанную область; проверки приказов в `Mobile` подтверждают именно это. Из них нельзя заключать, что весь поиск пользуется только запомненной игроком картой. Для OpenRTS политика знания местности требует собственного явного решения. [N005: проверка приказов](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/Mobile.cs#L940).

`ElevatedBridgeLayer` представляет мост отдельным слоем, хранит центры клеток на высоте и разрешает переход на слой у концов моста. Это подтверждает модель «поверхность + связи между поверхностями». Эта реализация помечена как предварительная; `Mobile` отдельно содержит ограничения выдачи приказов на произвольный слой. Это референс структуры, не доказательство полной поддержки разрушаемых многоуровневых мостов. [N006: мост](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/World/ElevatedBridgeLayer.cs#L47), [ограничение Mobile](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Traits/Mobile.cs#L769).

## 0 A.D.: клеточный дальний путь и геометрический короткий

**Наблюдения.** Интерфейс `ICmpPathfinder` различает дальний клеточный путь и короткий точный путь с clearance, радиусом области поиска и политикой учёта движущихся объектов. Результат — waypoints, цель может быть точкой или геометрической областью. Есть самостоятельная проверка целого движения между двумя точными позициями. [N007: интерфейс](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/components/ICmpPathfinder.h#L52).

В `CCmpPathfinder` маска проходимости вычисляется отдельно для каждого класса из глубины, уклона и расстояния от берега; препятствия расширяются на clearance класса. Нельзя безопасно объединять классы только по одинаковому радиусу, поскольку базовая проходимость грунта у них различается. `CheckMovement` сначала проверяет отрезок с радиусом против shapes препятствий, затем против сетки рельефа. Эта функция допускает некоторое перекрытие юнитов ради плавности, что не является подходящей готовой гарантией для OpenRTS. [N008: классификация и расширение](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/components/CCmpPathfinder.cpp#L650), [проверка движения](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/components/CCmpPathfinder.cpp#L857).

`VertexPathfinder` собирает ограниченный граф видимости из углов препятствий, расширенных на размер движущегося юнита. Учитываются точные начальные координаты и геометрическая цель; статические и мобильные shapes собираются отдельно. Граф перестраивается на запрос, поэтому сам файл предупреждает о высокой стоимости при большом числе объектов. Это пример короткого геометрического обхода, а не вариант глобального поиска для всех 10000 юнитов. [N009: короткий поиск](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/helpers/VertexPathfinder.cpp#L534).

В `Pathfinding.h` navcells имеют иной масштаб, чем terrain tiles. Классы включают clearance, пределы глубины, уклона и берега. `HierarchicalPathfinder` строит локальные связные области в chunks, связи соседних областей и глобальные компоненты; изменение карты обновляет затронутые части. Это позволяет отвечать на достижимость отдельно от подробного пути. [N010: масштабы и классы](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/helpers/Pathfinding.h#L131), [N011: связность](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/helpers/HierarchicalPathfinder.cpp#L362).

**Оговорка о весах.** Старый общий комментарий интерфейса упоминает terrain costs, но конкретный `LongPathfinder` этой версии использует JPS и геометрические горизонтальные/диагональные стоимости. `Pathfinding.h` описывает uniform-cost grid. Поэтому эта проверка подтверждает разделение масштабов и геометрии, но не поддержку произвольных весов болота/опасности дальним JPS. Добавление весов может лишить алгоритм исходных предпосылок. [N012: фактическая стоимость перехода](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/helpers/LongPathfinder.cpp#L389).

## Recoil: возможности движения, стоимость и физические контакты

**Наблюдения.** `MoveDef` содержит класс terrain speed, footprint, ограничения глубины и уклона, подводные параметры и прочность раздавливания. Есть отдельные коэффициенты для стоящих без приказа, занятых и движущихся мобильных препятствий, а также параметры heat/flow и выбор raw movement. Наличие этих полей не означает, что каждый поисковый backend использует их одинаково. [N013: MoveDef](https://github.com/beyond-all-reason/RecoilEngine/blob/d93c4daccd7c0f044714974554e9842b70736aa7/rts/Sim/MoveTypes/MoveDefHandler.h#L114).

`MoveMath` вычисляет terrain speed из типа грунта, уклона, высоты и профиля; отдельная перегрузка учитывает направление уклона. Другая функция классифицирует физические объекты: структура, движущийся, неподвижный/занятый мобильный объект. Проверки водных уровней также показывают опасность чрезмерного обобщения: код прямо описывает неполноту некоторых высотных случаев. [N014: скорость и блокировщики](https://github.com/beyond-all-reason/RecoilEngine/blob/d93c4daccd7c0f044714974554e9842b70736aa7/rts/Sim/MoveTypes/MoveMath/MoveMath.cpp#L75).

В QTPFS `NodeLayer` агрегирует скорость в bins и при построении карты выделяет структурную блокировку. `PathSearch` вычисляет стоимость отрезка с учётом средней стоимости пересекаемого узла, обратной скорости. Это адаптивная подробность и взвешивание связей, а не привязка точной позиции к одной клетке. Усреднение — компромисс: узкий непроходимый проход нельзя объявить проходимым только по хорошему среднему весу. [N015: NodeLayer](https://github.com/beyond-all-reason/RecoilEngine/blob/d93c4daccd7c0f044714974554e9842b70736aa7/rts/Sim/Path/QTPFS/NodeLayer.cpp#L179), [N016: стоимость](https://github.com/beyond-all-reason/RecoilEngine/blob/d93c4daccd7c0f044714974554e9842b70736aa7/rts/Sim/Path/QTPFS/PathSearch.cpp#L1516).

## Что следует заложить в OpenRTS

Ниже — предложения по результатам чтения, а не уже реализованные свойства OpenRTS:

| Решение | Практическое следствие и регрессионный сценарий |
| --- | --- |
| Физический профиль отдельно от политики приказа | Пехота и танк имеют разные clearance/terrain capabilities; агрессивность меняет реакцию на врага, но не разрешает физически проехать сквозь него |
| Достижимость отдельно от временного исполнения | Вражеский заслон не меняет связность рельефа; «сейчас блокирован», «нужна атака» и «по рельефу недостижим» — разные результаты |
| Traverse отдельно от Stop | Узкий транзитный участок можно пройти, но нельзя выбрать конечным местом. Если его нельзя освободить, нужна определённая реакция на блокировку/отмену |
| Точная позиция отдельно от навигационного индекса | Сдвиг внутри navcell, движение к точке под произвольным углом, несколько небольших юнитов внутри одной navcell. Соседство для контактов хранится своим пространственным индексом |
| Геометрия отдельно от растровой оценки | Круг огня остаётся кругом для урона. Навигационный штраф — производная оценка покрытия клетки/ребра, с собственной ревизией и policy ID |
| Классы знания отдельно от всезнающей карты | На неизведанном пути возможен предварительный маршрут с оговоркой неизвестности. Только обнаруженное препятствие вызывает раскрытие/перестроение; AI нельзя случайно дать скрытую информацию через общий cache |
| Связность учитывает capabilities и переходы | Граф для танка не совпадает с графом амфибии. Мост и дорога под мостом — разные поверхности со связями у въездов, а не одна высота для X/Y |
| Иерархия не подменяет проверку узких мест | Порталы/рёбра содержат доступный clearance и разрешённые профили. Средняя стоимость сектора не доказывает наличие прохода через сектор |
| Группа не равна максимальному юниту | Для режима «вместе» требуется пересечение возможностей всех участников и договорённость о том, разрешена ли колонна. Максимального радиуса недостаточно: амфибия и сухопутный танк могут иметь несовпадающие terrain masks |
| Кинематика отдельно от поиска | Ускорение, торможение, turn rate, движение задним ходом и interruptibility определяют исполнение. Сама возможность сменить точную цель ещё не реализует боевой stutter step |

Для стабильного кэша в дальнейшем важны профиль/clearance, ревизия постоянной геометрии, политика запроса, слой поверхности и версия знания игрока; временные occupancy/hazard данные не следует незаметно включать в ключ вечной компоненты связности. Детерминизм требует фиксировать порядок применения результатов и точные численные правила как для поиска, так и для контактного движения. Это выводы для проектирования; готовой общей модели кэша и API в этом исследовании не предлагается.
