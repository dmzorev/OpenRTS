## Обязательная последовательность

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| E0. Baseline | Зафиксировать journal/seed/правила и результаты работающих сценариев; замерить состояние до миграции | Повторяемые результаты движения/боя/N2/production, известны стоимость Step, hash, snapshot и allocations по отдельности |
| E1. Минимальная интеграция | Exact package pin/lock/notice; Frent.World на simulation owner; стабильный EntityId↔handle; инициализация типов компонентов, create/remove transaction; закрытые queries на границах фаз | Spawn/Delete/reuse, nonspatial entity и ошибки создания не повреждают mapping; Core/headless/Godot собираются; refs не выходят из фаз |
| E2. Пилот Production | Компонент ProducerState и query membership; lifecycle удаления; ID-порядок производителей; Spawn вне открытых queries. Остальная симуляция временно прежняя | Прежний production journal и state совпадают: cooldown/death перед выпуском, blocked exits, несколько производителей/очередей, repeat/cancel/place/rally; нет двойного занятия выхода |
| E3. Definitions и Actions | Составной compiled EntityDefinition с необязательными возможностями; UnitCatalog совместимый front-end; gameplay actions отделены от UI refs | Действие вызывается без UI; UI не меняет fingerprint; неизвестные ссылки/зависимости отклоняются до матча; Player-подобный тип не требует Spatial/Health |
| E4. Перенос массового состояния | По одному связному срезу: Identity/Spatial/Health → Orders/Motion/NavigationAgent → Combat/Presentation. Адаптировать MotionIndex к domain ID вместо packed index. Общие навигационные структуры оставить | Для каждого среза parity с baseline, sequential/parallel совпадают; после завершения нет EntityState мегакомпонента и дублирующего mutable состояния |
| E5. Завершение | Удалить миграционные stores/LegacyState и мосты; сохранить SimulationWorld как координатор/фасад; повторить полные проверки и профили | Единственный источник каждой записи; существующий headless/Sandbox работают; задокументированы новые форматы/пределы и фактический результат замеров |

E0–E2 — выполненный первый пакет реализации. Не начинаем с создания собственного универсального component registry. Пилот production выбран потому, что он имеет редкое сложное состояние и важные lifecycle/barrier случаи, но не требует одновременно переписать clearance и движение.

В E1/E2 допустимо, что ещё не перенесённые горячие поля живут в старом массиве, а производственные — уже в ECS. **У каждого поля один владелец**; запрещено поддерживать две изменяемые копии HP/позиций «для синхронизации». Успешный Spawn/Remove обновляет обе части мира атомарно на известной границе. При ошибке commit мир не публикуется как завершённый.

Непространственный тип сначала доказывается небольшим тестом lifecycle/query. Полноценный Player, экономика и исследования начинаются после E3 с реальной механикой; они не являются условием завершения ECS миграции.

## Решения, уже выбранные для реализации

- Frent0.9.1-beta, pinned; обычные компоненты данных и явные системы.
- Frent.World — хранилище: одна игра может использовать несколько ECS Worlds и обычные структуры. Пока создан только unit storage; Players и Projectiles не обязаны быть ECS entities.
- Прямые потребители освобождают SimulationWorld через using/Dispose; SimulationSession освобождает свой мир сама.
- Actor = domain entity; отдельный суперкласс/мегакомпонент не создаётся.
- OpenRTS EntityId остаётся внешним ID; Frent handles только внутри симуляции.
- Fixed tick, fixed-point, координатор фаз, канонические конфликты и публикация копий сохраняются.
- Структурные изменения в domain commit за пределами queries; не полагаемся на автоматический Frent buffer для порядка.
- Частые состояния — значения/флаги; обычные archetype компоненты как начальный вариант.
- Навигационные карты, индексы и общие caches не переносятся в ECS ради единообразия.
- Игровые definitions отделены от состояния; UI bindings ссылаются на gameplay actions.
- Системы заменяются в composition root под явные доменные контракты, без универсального IEcsWorld.

## Опции с отложенным выбором

| Опция | Начальный вариант | Когда возвращаемся |
| --- | --- | --- |
| Sparse компоненты | Не применять по умолчанию | Profiling показывает частый structural churn конкретной редкой возможности; проверяем цену query и потерю chunk API |
| Хранение mounts/queues/путей | Существующие массивы/объекты с единственным владельцем | Измерены GC/working set/cache misses; сравнить inline малые наборы и пулы переменных данных |
| Параллельная обработка ECS chunks без копий | Текущие внешние jobs и барьеры | Измерена стоимость копий/merge; есть доказуемое владение диапазонами и независимость записей |
| Снаряды как ECS entities | Оставить текущий пул | Появились нужные комбинации компонентов/единые queries; переход доказан сценарием |
| Native prefabs/clone | Compiled definitions и explicit initialization | Доказаны отсутствие alias mutable state и экономия на spawn; не использовать clone живого юнита как definition |
| ActorRef фасад | Пока EntityId и конкретные read APIs | Появился реальный редактор/скриптовый потребитель |
| Библиотечная сериализация/инспектор | Только диагностика при необходимости | Не подменяет canonical gameplay hash или будущий полный save/restore |
| Автоматическое планирование систем | Явный список фаз | Измерены независимые участки, заданы права на внешние ресурсы и воспроизводимые барьеры |
| Dynamic loading модулей | Статическая сборка и регистрация до матча | Есть игра, которой нужен mod runtime/hot reload; отдельно решаются type registration и воспроизводимость |

Это опции реализации, не поводы остановить ближайший пилот и запросить выбор пользователя.

## Приёмка и измерения

До переноса сохраняем baseline текущей реализации, после каждого среза повторяем только относящиеся к нему проверки. Финал — `tools/dev.sh test`, headless production/buildings/combat/navigation и существующие Godot verify-сценарии. Важны не только кадры: отдельно сравниваем события, командный журнал и продолжение состояния после пропущенного рендера.

Обязательные случаи: stable ID при recycling; удаление сущности, указанной в приказе; несколько producer с одним выходом; смерть/ремонт в тот же тик; отмена/повтор задачи; готовое здание и невалидное размещение; динамический footprint; packed/archetype removal; cooldown/burst на Move; snapshot lease при перестройке store; отсутствие пустых Spatial данных у Player-подобного объекта. Component refs не хранятся в jobs/UI и не переживают structural commit.

Нагрузки E0/E2/E4:1000/10000 объектов с разными capability-наборами; отдельный100000 scan для оценки storage, не как обещание армий такого размера. Измеряем создание/удаление, query/Step p50/p95, allocations после прогрева, managed memory, snapshot/hash отдельно, полный cold first order и steady state. Для production — число реально работающих фабрик/выпусков, для combat — mounts/projectiles/targets, для navigation — карта/профили/запросы. Среда, JIT, Release, число тиков и workers записываются рядом с результатами.

Текущий gate: при ухудшении p95 Step более10% на сопоставимом steady-state сценарии либо необъяснённом росте steady allocations относительно baseline перенос горячих срезов останавливается до объяснения/исправления. Это предварительный инженерный порог, не обещание10% точности всех замеров. Сначала оцениваем шум несколькими запусками. Ограниченные allocations реального Spawn и роста ёмкости отделяем от allocations на неизменной membership; первый перенос фиксирует их отдельно, см. verification/015. Отдельная цена одноразовой регистрации/создания не прячется в среднем Step. Если проблема в интеграции — исправляем; если в библиотеке и обход дороже смены — сравниваем EasyEcs на том же пилоте до E4.

ECS не отменяет N4: clearance/global invalidation/холодный поиск и пропускная способность тесной толпы измеряются и исправляются независимо. Не маскируем регрессию навигации быстрым тестом неподвижных сущностей.

## Что требуется от пользователя

Для выбора библиотеки и технического пилота новых продуктовых решений нет. Исследование, интеграцию, тесты, локальные измерения и подготовку документации можно выполнить самостоятельно в рамках следующего этапа. Production-пилот и E3 выполнены; Spatial/Health и Orders/Motion/NavigationAgent уже в ECS; следующий пакет — Combat/Presentation, затем оставшийся mapping/legacy cleanup. Общая миграция ещё не закончена.

Позже полезны целевые CPU/память/OS и бюджет тика конкретной игры, а после рабочего Sandbox — оценка поведения. Новая схема экономики, сетевой режим, авторские моды/горячая загрузка требуют отдельных требований по мере их появления. До этого они не блокируют E0–E2.
