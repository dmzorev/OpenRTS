# Архитектура OpenRTS поверх Frent

Статус: целевая модель следующего этапа; текущий SimulationWorld ещё использует EntityState[]. [Выбор и альтернативы](README.md), [переход](migration.md).

## Entity и Actor

**Actor — доменное название игровой сущности, а не дополнительная runtime-система.** Его реализация — Frent Entity с выбранным набором компонентов. Отдельные Actor superclass, ActorComponent с копией всех полей, ActorSystem с логикой всего мира и второй ActorId не нужны.

Сохраняем существующий **OpenRTS EntityId** как стабильный игровой идентификатор команд, целей, событий и опубликованных кадров. Внутри симуляции есть соответствие EntityId → Frent.Entity и компонент Identity с игровым ID/ссылкой на тип. Внутренний recycled handle не выходит к Godot или сети и не определяет порядок footprint/приоритетов. Все изменения существования проходят один lifecycle-вход координатора, который синхронно обновляет mapping и membership.

Слово Actor не обязывает немедленно переименовывать UnitAction/UnitDefinition. Для справочника общих составных типов предлагаем EntityDefinition; имя можно уточнить при первом переносе Content. Тонкий ActorRef/read-only view допустим позже для инструментов, если появится потребитель. Он не владеет состоянием, не держит ref на компонент между фазами и не вызывается виртуальным Tick для каждой сущности.

Player при появлении экономики — такая же ECS Entity с PlayerState/Research/Population по потребности, без фиктивных Position/Health/Locomotor. PlayerId обозначает участника матча, EntityId — его игровое состояние; связываем их явно. Аккаунт, соединение и локальный выбор не становятся компонентами authoritative Player. Пустой Player до первого реального поля не создаём.

## Три разных уровня данных

| Уровень | Содержимое | Кто изменяет |
| --- | --- | --- |
| Исходный контент | YAML, model/animation assets, UI layout | Автор игры/подготовка Content |
| Compiled definitions | Immutable параметры типа, возможности/зависимости, оружие, locomotor, build data, игровые action IDs | Content компилирует до матча; runtime не записывает обратно |
| Runtime components | Позиции, HP, cooldown, задачи, активные приказы, временные модификаторы | Соответствующая система симуляции |

Definition — рецепт, **не entity в живом store**. Content валидирует зависимости и ссылки, разрешает имена в стабильные ID и готовит конкретные типизированные данные. Spawn создаёт компоненты только заявленных возможностей. Повреждённый юнит меняет своё Health, улучшение игрока — effective modifier/Player state, а не общий шаблон всех юнитов.

Сначала сохраняем существующий YAML как совместимый вход. Затем отделяем `GameplayActions` от `ActionPanel` references: удаление UI кнопки не удаляет способность и не меняет gameplay fingerprint. Model/UI bindings остаются вне Core gameplay definitions. Не вводим `Dictionary<Type,object>` как способ доступа ко всем горячим компонентам и не разбираем YAML при Spawn/Step.

## Разделение состояния

Имена ниже — границы ответственности для пилота, не список заранее создаваемых файлов.

| Данные | Начальный вариант | Замечание |
| --- | --- | --- |
| Identity, definition reference, ownership | Компактные компоненты | Owner не заменяет PlayerId/отношения |
| Spatial: Position/Previous, физическое тело | Struct/definition reference | Нет зависимости от Model.Size; только у объектов карты |
| Motion/navigation agent | Связные struct-компоненты | Цель, остаток скорости, ожидание/уступание и локальный путь должны полностью сохраняться |
| Health | Struct | Базовые immutable параметры отдельно от текущего HP |
| Orders | Активный приказ + bounded queue state | Сначала перенос без смены правил FIFO/валидности |
| Weapons/abilities | Runtime mounts + ссылки на definitions | До8 независимых cooldown/burst; граната/ремонт остаются существующим backend |
| Production | Компонент со ссылкой на существующий ProducerState | Одна ECS membership; не дублировать параллельный registry производителей |
| Semantic presentation | Направления, playback, состояния | Без Texture/SpriteFrames/Godot types |
| Player | Только необходимые данные реальной экономики | Отложен до потребителя, но отсутствие Spatial поддерживается сразу |

Компонент должен объединять данные, которые часто читаются/пишутся вместе. Не дробим каждый скаляр в отдельный компонент и не переносим весь EntityState в один вечный мегакомпонент. Временный LegacyState допустим как ограниченный миграционный мост с явным этапом удаления.

**Переменные данные.** В первом переносе сохраняем текущие arrays/queues/ProducerState с единственным владельцем; это позволяет сравнить семантику отдельно от оптимизации памяти. Потом измеряем отдельные пулы/handles, InlineArray для малых фиксированных наборов и уплотнение холодных записей. Не кладём очередь256 задач внутрь каждого горячего компонента и не выделяем пустой List всем10000 объектам. Ни свой pool переменных путей, ни MotionIndex не являются попыткой написать ещё один ECS.

**Вне ECS остаются** карта/terrain и её версии, пространственные индексы, общие поля/деревья маршрутов, геометрические acceleration structures, RNG/тик/командный журнал и FrameExchange. У них другой характер доступа. Снаряды сначала остаются в существующем компактном пуле: отдельная ECS миграция возможна по измерениям, без обязательства «всё в Entity».

## Фазы и изменения структуры

Координатор SimulationWorld владеет Frent.World на потоке симуляции. Query-системы вызываются явно; `World.Update()`, `IUpdate` и lifecycle callbacks Frent не исполняют игровую логику.

```mermaid
flowchart LR
  C[Команды и изменения карты] --> O[Приказы]
  O --> N[Навигационные jobs + барьер]
  N --> M[Движение]
  M --> B[Оружие и снаряды]
  B --> D[Урон / ремонт / смерти]
  D --> P[Производство и размещение]
  P --> V[Семантическое представление]
  V --> F[Копии кадров и события]
```

Границы из текущего Step сохраняем до осознанной смены правил. Общая идея «один ECS command buffer применяем в конце тика» здесь неверна:

- команды размещения меняют terrain до движения;
- урон и смерти применяются до производства: мёртвый завод не выпускает юнит;
- успешный Spawn виден следующему производителю в том же проходе: одинаковый выход нельзя занять дважды;
- событие смерти, снятие footprint, прекращение заказов/очередей и удаление identity — доменная транзакция, а не побочный эффект OnDestroy.

Query по производителям сначала собирает стабильные ID и завершается. Затем координатор последовательно обрабатывает их и при каждом успешном выпуске обновляет ECS и MotionIndex. Нельзя оставить открытый query, рассчитывая на немедленную видимость Frent.Create для следующих производителей. В каждой такой транзакции до успешной валидации не снимаем готовую задачу и не публикуем частичную сущность.

В горячих queries структурные изменения запрещены нашим контрактом даже там, где Frent их допускает/откладывает. Системы формируют **доменные результаты**, например Damage/Death/Spawn request. Координатор применяет их с заданным конфликтным порядком за пределами всех enumeration. Это существующая игровая семантика, не универсальный дубль ECS command buffer. Component refs/spans не переживают структурные изменения, ожидание jobs или публикацию.

## Параллельность

ECS выбираем ради данных/запросов; число потоков — независимый вопрос. Baseline: явно запускаемые jobs получают immutable вход или зафиксированный диапазон, пишут только принадлежащий им output. Координатор ждёт всю обязательную работу и применяет результаты в доменном порядке. Величина gameplay Tick не равна счётчикам ECS.

Нельзя подменять порядок боевых конфликтов или расход RNG порядком chunks. Для независимой арифметики сортировка каждого прохода не нужна; она нужна там, где есть tie-break, выдача ID/TaskId, конфликт или каноническая сериализация. Существующие отсортированные ID списки можно кэшировать и обновлять при lifecycle, вместо сортировки всех10000 на каждом этапе.

Базовый пилот использует внешние jobs над копиями/буферами. Zero-copy chunk jobs возможны отдельной оптимизацией: freeze структуры, владение диапазонами, отсутствие alias managed data, явный join до commit. Frent parallel EC Update для этого не подключаем автоматически. Read/write компоненты не раскрывают скрытые записи в общую карту, индекс или List: они также входят в контракт системы.

## Как заменять игровые системы

ECS делает компоненты/queries доступными разным реализациям, но сам не определяет совместимость механик. Игра собирает **конкретный список систем** в composition root до начала матча. Реализация фазы знает разрешённые входы/выходы и обязательства, а не получает неограниченный доступ ко всем private полям World.

Например, другой pathfinder получает NavigationRequests, terrain/locomotor/knowledge view и фиксированный бюджет; возвращает NavigationResults/статус. Другой combat resolver работает с оговорёнными Damage/Repair результатами. На первый реально заменяемый участок вводим узкий доменный контракт, затем проверяем две реализации. Не создаём interface для каждой тривиальной операции заранее.

Две замены различаются:

- **Альтернативная реализация той же механики** сохраняет схемы данных, фазовые обязательства и результаты сценариев.
- **Новая механика игры** может добавлять компоненты/definitions и менять правила; совместимость gameplay fingerprint/реплея при этом не обещается.

Core и игровые systems могут использовать нативные Frent queries. Godot, команды и кадры — через стабильные контракты OpenRTS. Не оборачиваем весь Frent в IEcsWorld с дубликатами Query/Add/Remove: это вернуло бы стоимость собственного ECS. Замена gameplay system должна быть дешёвой; замена всей ECS библиотеки остаётся отдельной миграцией.

## Сохранение и хеширование

Сохраняем каноническую схему игрового состояния по стабильным domain IDs. В hash не входят archetype order, component type numbers, recycled slots, делегаты и внутренние caches Frent. RNG, активные приказы, cooldown, задачи, остатки движения, cache cursors/бюджеты, влияющие на будущий результат, остаются authoritative независимо от места хранения.

На этапе parity сначала требуем прежний hash при прежних правилах. Если разбиение требует новой схемы, добавляем нормализованное сравнение полей со старой реализацией; новый номер формата вводим явно и не обновляем golden hashes без объяснения. Полный save/restore всё ещё отдельный будущий этап: ECS snapshot или копия ссылок не заменяет его.
