# Масштабирование основы OpenRTS

Цель — наземные RTS с 10000+ объектами и большими картами. Нужно различать число существующих объектов, число объектов в кадре, число движущихся юнитов, запросы маршрутов и активные боевые взаимодействия. Статическое отображение 10000 объектов не устанавливает пропускную способность симуляции.

**Начальное решение для отображения.** Использовать MultiMesh для однотипных диагностических маркеров. Godot описывает GPU instancing как способ уменьшить стоимость отдельных draw calls и указывает, что MultiMesh рассматривается как один объект видимости. Поэтому минимальный стенд использует один пакет, а последующая большая карта потребует чанков. [Документация MultiMesh](https://docs.godotengine.org/en/stable/classes/class_multimesh.html).

**Требования к следующим исследованиям.** Хранение состояния должно позволять плотные массивы без отдельного узла сцены на юнит. Поиск целей и столкновения требуют пространственных индексов вместо всех пар. Навигация оценивается на массовом изменении приказов и узких проходах; выбор A*, иерархии или flow fields определяется этими сценариями. Воспроизводимые параллельные задачи рассматриваются вместе с моментом потребления результатов, а не добавляются поверх готовой семантики.

Нагрузочные сценарии включают разреженную большую карту, плотное скопление, массовый приказ движения, массовую смену целей и ограниченную видимую область. Результаты сохраняют оборудование, сборку, размеры карты, число активных юнитов, частоту тика, p50/p95 времени тика, выделения памяти, ожидание работников и время подготовки представления.

**Граница вывода.** Первый стенд подтверждает загрузку контента и создание статических экземпляров. Он не моделирует поиск пути, бой, обновление 10000 объектов за тик или поведение на большой карте. Порог приемлемой производительности определяется отдельно для сценария игры.
