# Footprint зданий, размер тел и изменения навигации

Дата: 2026-11-04. Исследование для N2: многоклеточные объекты, изменение terrain/прохода/остановки, размеры подвижных тел и попадания по границе. Выборочно изучены 13 первичных файлов OpenRA и 0 A.D. Источники закреплены на commit SHA и проверены загрузкой raw-файлов; размеры и SHA-256 записаны в [sources.json](sources.json). Исходники лицензированных референсов не переносились в MIT-проект. Это архитектурный разбор, без сравнительного запуска движков или измерения их производительности.

## Вывод

Для OpenRTS стоит разделить три вещи: **геометрию тела/цели**, **накладываемые на навигацию свойства footprint** и **видимые слои модели**. Проходимая часть здания может оставаться частью цели для атаки, не создавая отдельный блокирующий круг посередине. Декоративная крона, дым, радар и открытая дверь не определяют физику.

Базовая карта и живые накладывающие объекты — источник истины; готовые значения navigation grid — вычисляемый результат. Для небольшого числа изменений достаточно пересчитывать затронутые клетки из живых объектов в стабильном порядке установки. Сохранение «предыдущего значения» внутри каждого объекта не обеспечивает корректное удаление перекрытий в произвольном порядке.

### Почему previous-value недостаточно

Наша проверка поведения по S02: база grass; A меняет её на forest, B поверх A — на mountains. Если сначала удалить A и просто вернуть сохранённую grass, активный B исчезнет из эффективной карты. Затем удаление B восстановит forest уже отсутствующего A. Это показывает границу подхода, а не основание копировать другой сложный механизм целиком.

Для требования пользователя предлагается `effective = fold(base, live overlays ordered by placement)`. Последний объект имеет приоритет. Порядок — монотонный placement ordinal либо EntityId, если ID гарантированно возрастает и не переиспользуется; **не индекс плотного массива**, меняющийся при packed removal. Удаление нижнего/верхнего/среднего объекта должно давать одинаково определённое восстановление.

Необязательные поля можно разрешать независимо: отсутствующий Terrain/Traverse/CanStop наследует нижний слой; явно заданное поле перекрывает соответствующее поле. Это выбранная семантика OpenRTS, источники не доказывают её единственность. Верхний `Traverse=true` снимает нижнее общее ограничение клетки, но не отменяет запрет Locomotor для текущего terrain; чтобы провести танк по воде, нужен подходящий terrain/profile. `CanStop=true` также не делает запрещённый terrain доступным.

Пока небольшое число зданий меняется редко, пересчёт списка объектов в затронутых клетках проще отдельного per-cell стека. При большом числе изменений можно добавить spatial index overlays; публичная семантика от этого не меняется. Нельзя обещать O(1) или масштабирование без замера.

## Размеры и точная геометрия

0 A.D. использует clearance при проверке движения и растеризации; terrain clearance расширяется по navcells, причём код [S09](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/components/CCmpPathfinder.cpp) отдельно отмечает консервативность квадратных углов расширения. Это подтверждает сам tradeoff между дискретной проходимостью и точной формой, а не конкретную оптимальность будущей сетки OpenRTS.

Предлагаемый N2 для OpenRTS: постоянная lattice мировых координат для clearance routes, независимая от terrain.CellSize, и отдельные exact circle/axis-aligned box проверки полного отрезка. Terrain samples остаются носителями свойств; частично закрытые клетки можно представить локальными прямоугольниками, не запрещая целиком всё содержимое sample. Смена масштаба terrain не должна сдвигать обязательные узлы clearance-поиска. Точные start/goal и свободное угловое движение сохраняются.

Фиксированная lattice, например шаг 512, **не гарантирует полноту непрерывного планирования**: узкий несоосный проход может быть физически доступен, но не содержать подходящих узлов/рёбер. Прямой отрезок и локальная геометрия способны решить часть таких случаев; необнаруженный путь остаётся известным ограничением конечной выборки. Это следует показывать отдельным тестом, не называть математической недоступностью области. Размер шага и объём clearance-кэшей требуют измерения на больших картах.

Ключ clearance-профиля должен учитывать Locomotor, форму/размер тела и ограничения рельефа (если вводятся slope/step/depth). Перестройка должна учитывать старую и новую геометрию, а не только новый прямоугольник. Простейшая безопасная версия — смена общего nav revision; локальная инвалидация — оптимизация после проверки корректности.

Два состояния с одинаковым effective grid могут иметь разное будущее после удаления верхнего слоя. Поэтому base map, живые скрытые overlays и их порядок входят в authoritative state/hash. Если скрытый слой изменился, но итоговая карта прежняя, можно сохранить nav revision, однако хеш игрового состояния всё равно должен измениться.

## Дальность и splash по границе

[S05 SpreadDamage](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/Warheads/SpreadDamageWarhead.cs) перебирает actors, находит ближайшую активную HitShape и выбирает DistanceFromEdge; это один расчёт эффекта для victim, а не отдельный урон за каждую форму. [S06 Rectangle](https://github.com/OpenRA/OpenRA/blob/9636b63eaee62fcb60ef2e896e7985bdf2f1ee68/OpenRA.Mods.Common/HitShapes/Rectangle.cs) считает расстояние до границы прямоугольника, равное нулю внутри него. Есть и альтернативы center/closest-targetable-position: правило расстояния — явный выбор, не случайное свойство spatial index.

В [S12 RangeManager](https://github.com/0ad/0ad/blob/61a3b9507d974084e6badb88a0826bd89a6d5b8b/source/simulation2/components/CCmpRangeManager.cpp) subdivision Add/Move учитывают размер, результаты distinct и сортируются по ID. AccountForSize расширяет диапазон источником/целью, но итоговая обычная проверка приблизительно circle-circle. Этого недостаточно как точной проверки сложного footprint; для OpenRTS это прежде всего пример broad phase с extents и стабильного результата.

Предлагаемые правила:

- Для круга — расстояние до поверхности; для здания — минимум по объединению занимаемых клеток/прямоугольников. Пустые клетки схемы исключены, центр здания и bounding box не подменяют его форму. Если в будущем passable-двор не должен быть целью, потребуется отдельный targetable mask; это новая семантика, а не скрытая связь с Traverse.
- В range-проверке явно определить, откуда измеряется дальность источника: от поверхности тела либо от отдельного weapon origin. Нельзя применять разные соглашения при acquisition, chase, fire и repair.
- Aim point выбирается на ближайшей занимаемой части здания; иначе снаряд в пределах range может направляться к недостижимому далёкому центру или стрелок пытаться войти внутрь здания.
- Broad phase обязан находить большой объект, центр которого вне радиуса, если граница попадает в него. Варианты: индекс bounding boxes по нескольким buckets с dedup либо раздельный индекс крупных static объектов. Только padding максимального юнита может стать дорогим для огромных зданий.
- AoE: кандидаты → dedup ID → exact intersection/min-distance → один ApplyEffect на объект за explosion. Несколько клеток одного здания, найденных в разных buckets, не умножают урон. Число попаданий разных снарядов остаётся независимым.
- Для projectile sweep учитывается размер цели и всё относительное движение за тик; статическая форма здания и круг/box движущегося тела требуют соответствующей narrow phase. Пограничное касание нужно определить одинаково во всех системах.

## Обязательные граничные сценарии

| Область | Проверка |
| --- | --- |
| Слои | A→B; removeA/removeB в обоих порядках; три слоя; packed removal соседнего actor; скрытый слой меняет hash; base edit под overlay |
| Частичные свойства | Верхний Terrain без Traverse; верхний запрет остановки без смены terrain; снятие одного поля не стирает другие; forest/mountains поверх road/water |
| Динамика | Здание поставлено на будущий сегмент уже рассчитанного пути; удалено до следующего шага; cost меняется без blocked; CanStop меняется у текущей цели; карта после смерти восстанавливается |
| Размещение | Полностью/частично вне карты; клетка на границе; fractional anchor; пересечение с телом/его текущим swept переходом; безопасный проезд под визуальным слоем |
| Размеры | Пехота проходит, техника нет; круг/box у угла; диагональная щель; противоположные крупные тела; проход с доступными endpoints и недоступным внутренним отрезком |
| Рельеф | Step/slope/depth точно на лимите и за лимитом; одинаковая геометрия при разном terrain.CellSize; частичный obstacle не закрывает свободную часть sample |
| Бой | Край большой цели в дальности при далёком центре; взрыв за пределами центра здания; несколько клеток/несколько buckets дают один урон; соседние здания получают каждый свой; круг касается AoE только краем |
| Представление | Ruin остаётся видимым без прежнего overlay; radar/doors/working не меняют gameplay footprint; draw priority не зависит от плотного массива |
| Воспроизводимость | 1/несколько workers; обратный порядок выполнения jobs; старый FrameLease после nav revision; отменённый пересчёт не публикует частичную карту |

## Ограничения исследования

OpenRA исследован на `9636b63…`, 0 A.D. — на `61a3b95…` архивного зеркала; это не заявление о свежести upstream. Не изучались все моды, подробности terrain deformation, многоуровневые мосты, навмеши или production placement UI. Наличие соответствующих механизмов у референсов не доказывает корректность, скорость или полноту реализации OpenRTS. Для текущего этапа важнее детерминированные собственные тесты и отдельные замеры map composition, clearance rebuild, exact motion и combat queries.
