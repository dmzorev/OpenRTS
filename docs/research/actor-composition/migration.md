# Предлагаемый план рефакторинга

> Обновление2026-11-05: по уточнённому требованию пользователя выбрана готовая ECS библиотека. Рекомендации сначала создавать собственные stores и отложить ECS-пилот заменены [выбором Frent](../ecs-selection/README.md) и [новым планом](../ecs-selection/migration.md). Ниже сохранён исходный анализ; runtime по нему не мигрировал.

Дата: 2026-11-05. **Предложение, не выполненная миграция.** [Обоснование и альтернативы](README.md). Новых продуктовых решений для первого технического среза не требуется; принятие общей модели и более глубокая миграция обсуждаются отдельно.

## Порядок работ

| Срез | Изменение | Проверяемый результат |
| --- | --- | --- |
| R0. Зафиксировать исходное поведение | Команды, границы фаз, lifecycle, записи компонентов, baseline hash и профили | Есть сравнение со старой реализацией, не только тест «новое совпало с новым» |
| R1. Отделить Production | Вынести существующие ProducerState/очереди и обработчики в конкретный модуль; World остаётся координатором. Дать ему узкий доступ к actor lookup/определениям, проверке выхода, приказам и lifecycle-операциям | ProducerState больше не является private-состоянием общего World. Новое правило очереди не требует менять EntityState, Combat и навигацию. Сохраняются текущие байты канонического состояния/исходы, если формат не меняется |
| R2. Отделить объявления возможностей | Ввести компилируемые ActorDefinition/планы типа, необязательные capability definitions; разделить игровые Actions и UI ActionPanel refs. Старый UnitCatalog/YAML временно остаётся совместимым входом | Игровое действие можно вызвать без кнопки; удаление/переупорядочивание UI bindings не меняет набор способностей и gameplay fingerprint. Зависимости и неизвестные action refs обнаруживаются до матча |
| R3. Добавить общую identity/lifecycle и PlayerActor | Общий EntityId/definition lookup; пространственные actors и player state имеют разные runtime-наборы. Ввести PlayerId и явное соответствие actor. Начать с конкретных необходимых Player данных, не писать пустую экономику | Player создаётся без Health/Spatial/Locomotor и не попадает в MotionIndex, выдачу мест, рендер/selection. ActorCount и SpatialCount различаются. Ownership не смешивает PlayerId с EntityId |
| R4. Разделить Combat/Orders/Movement state и исполнение | Последовательно вынести связанные группы данных и системы; отделить сбор опубликованных DTO. Каждый перенос включает teardown и сериализацию | Новый эффект здоровья не переписывает движение; ActorState перестаёт быть одной универсальной структурой. Все системы не получают неограниченный World и не вызывают чужой Tick |
| R5. При необходимости сравнить storage backend | Пилот на реальном Motion/Combat наборе: нынешнее/раздельное хранение и готовый ECS-кандидат. Согласованный состав данных, правила, команды и бюджет | Решение по библиотеке принимается по поддерживаемости и сопоставимому профилю, с проверкой API/лицензии, а не по микротесту Position+=Velocity |

**Первый разумный срез — R0/R1**, а не массовое переименование Unit → Actor. Производство уже имеет отдельное редкое состояние, относительно небольшой объём и показательные зависимости. Это позволяет проверить модульную границу, не переписывая алгоритм навигации и одновременно все массивы.

R2/R3 логично выполнить **до экономики**, чтобы затем не делать Player фиктивным юнитом. Сложное изменение hot storage можно оставить последующим независимым шагом. Если уже пилот R1 показывает, что специализированные stores лишь дублируют готовый ECS и усложняют код, стоит перенести сравнение R5 раньше, до массового переноса остальных систем.

## Что сохранить при R1

- Приказы и изменение карты видны в прежних фазах; бой и удаление погибших происходят до производства.
- TaskId, выбор кратчайшей очереди, tie-break по EntityId, хвост повторов, цена/длительность и прогресс сохраняются.
- Невалидное размещение не расходует ready task и не выдаёт EntityId; выходы проверяются с прежними размерами/занятостью.
- Успешный выпуск должен стать видимым следующей очереди в тот же production-проход, иначе два производителя могут выбрать один свободный выход.
- Гибель/удаление производителя снимает все его состояния и подписки. Непереиспользуемый ID и packed removal не меняют очереди другого актора.
- Производственная публикация WorkingState/ExitAnimation может строиться из результата модуля; она не должна требовать чтения private ProducerState из общего CopyPoses.
- Сохраняются quota32, ограниченный поиск выхода и остальные существующие правила. Это рефакторинг, не обещание нового throughput.

Для передачи структурных изменений достаточно конкретных запросов/операций жизненного цикла и согласованных точек применения. Не требуется до первого среза создавать универсальный event bus, reflection scheduler, сериализатор любых object или набор пустых интерфейсов. Сам по себе `ProductionSystem.Tick(world)` с прежними правами доступа также не считается выполненным разделением.

## Definitions и runtime: контракт R2

Три разных уровня:

1. **Content options** — результат чтения YAML и параметров матча. Они могут быть изменяемыми во время загрузки; runtime их не получает.
2. **Compiled definitions** — валидированные неизменяемые шаблоны, стабильные ссылки/индексы и план состава конкретного типа. Совместно используются экземплярами.
3. **Actor/component state** — актуальное HP, очередь, ресурсы, modifiers, cooldown и другие меняющиеся данные конкретного экземпляра.

Наличие ActorDefinition не означает хранить всю runtime-логику в нём или превращать его в конструктор World. Capability registration описывает параметры/зависимости/инициализацию/запись состояния конкретной системы. Порядок исполнения систем остаётся отдельным контрактом.

Runtime query не обязан каждый раз разбирать название YAML трейта или искать object по Type. На горячем пути используются типизированные хранилища/подготовленные выборки; именованные instance keys нужны прежде всего компиляции, командам и диагностике. Например, несколько оружейных mounts и production queues должны сохранять собственные идентификаторы, а не коллапсировать в один компонент «по CLR type».

Рефакторинг Actions должен сохранить удобство короткого объявления продукта: цена/время берутся из buildable определения, override принадлежит игровому действию производителя. UI ссылается на Action ID. Автогенерация панели по списку действий допустима как адаптерная возможность, но наличие действия не определяется наличием виджета.

## Lifecycle, ID и воспроизводимость R3/R4

Registry является единственным владельцем выдачи ID и переходов create/activate/remove. Частично созданный actor не публикуется и не попадает в запросы. Зависимости и начальное состояние проверяются до активации; отказ не оставляет половину компонентов или расходованную задачу. ActorRef не хранит постоянный dense index, а `ref`/Span не переживают реорганизацию storage.

Будущие PlayerId и EntityId принадлежат разным пространствам идентичности. Создание player actors в общем реестре может изменить порядок выдачи EntityId и старые fixture ID: это нужно явно учесть в версии журнала/сценариев, а не маскировать одинаковым underlying uint. Не следует обещать сохранение старого хеша при добавлении нового authoritative Player state.

Общее число акторов и число пространственных поз не обязаны совпадать. Потребители SimulationReport/FrameExchange сейчас используют совпадение этих чисел: их контракты необходимо мигрировать явно. Player views добавляются при появлении реальных данных, с тем же FrameLease lifetime; не нужно давать игрокам фиктивную EntityPose.

Каждая система перечисляет authoritative state для canonical hash/будущего save. Новый формат меняется осознанно при изменении состава/схемы состояния. Порядок записи — по устойчивым ID и стабильным идентификаторам возможностей/экземпляров, а не CLR hash, runtime Type registration или archetype iteration. Буферизация structural changes обязана сохранять порядок выдачи ID и игровые барьеры.

Существующие cache cursors/бюджеты навигации остаются частью состояния. Не всё содержимое ECS-пула является кэшем; и не всё расположенное в Dictionary является authoritative. Это свойства данных, а не контейнера.

## Приёмка

Минимальные проверки для соответствующих срезов:

- Все прежние scenarios/worker parity, включая packed removal, динамические footprint, отмену поиска и pinned leases.
- Производство после смерти, общий занятый выход, cancel/repeat/ready task, несколько очередей и ID порядок.
- Player без пространственных компонентов рядом с10000 пространственных actors: membership не меняет навигационные профили/выдачу мест и не создаёт видимые спрайты.
- Один definition порождает два независимых runtime состояния: повреждение, исследование или cooldown одного не меняет шаблон и другого игрока.
- Отсутствующая capability dependency и невалидная комбинация отклоняются при компиляции; несколько named instances валидируются отдельно.
- Удаление/смена UI панели не убирает AI/программное действие.
- Новый компонент/система не полагаются на порядок dense storage, регистрацию CLR типов или завершение workers.
- Если сохраняется формат записи, старый и новый backend дают один канонический результат. Если схема меняется — отдельно сравниваются игровые исходы и фиксируется новый формат, без заявления об автоматической совместимости старых реплеев.

## Измерения перед выбором ECS backend

Измерять одинаковые сценарии, отдельно:

- Только движение; движение с навигацией; бой и снаряды; производство/частые spawn-remove; подготовка кадров; canonical hash.
- Память/аллокации и время этапов, холодный запрос/смену карты отдельно от steady-state.
-10000 и более объектов, смешанные наборы возможностей, разное число workers; холодные компоненты игроков/производителей отдельно от массовых movers.
- Стоимость добавления/удаления компонентов и invalid refs после структурных изменений, если выбран ECS с динамической композицией.

Не следует приписывать рост/падение скорости самому слову ECS. Если пик находится в построении глобального clearance, нужна работа N4; смена контейнера не доказывает устранение этого пика. Новых performance-результатов этот исследовательский пакет не содержит.
