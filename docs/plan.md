# План подготовки и реализации OpenRTS

Первый результат — небольшой проверяемый RTS движок с headless запуском и Godot стендом. Этап считается завершённым по работающему сценарию и проверкам, а не по количеству созданных интерфейсов. Календарные оценки появятся после первого каркаса и измерений.

**Текущее состояние на 3 ноября 2026 года.** Подготовлены README, MIT лицензия, архитектурные договорённости и этот план. Реализация не начата. Каталог OpenRTS на момент проверки не был Git репозиторием. Найдены .NET SDK 10.0.105 и runtime 10.0.5. Выполнена проверка версии локального Godot: 4.7.2.stable.mono.official.ed1daf0bf.

Godot расположен в `/Users/dmzorev/projects/games/Godot_mono.app/Contents/MacOS/Godot`. Это проверенное локальное окружение; минимальные поддерживаемые версии SDK и движка ещё предстоит зафиксировать проверкой сборки. Установка инструментов сейчас не требуется.

**Расположение проектов.** Основная работа идёт в `/Users/dmzorev/projects/games/OpenRTS`. На старте headless инструмент, тесты и минимальный Godot стенд находятся здесь же: это позволяет менять контракт и оба потребителя одним изменением. Отдельный репозиторий нужен для самостоятельной демонстрационной игры, особенно с GPL зависимостями и отдельными лицензиями ассетов.

Предлагаемая структура после первого этапа реализации:

```text
OpenRTS/
  src/OpenRTS.Core/          # Независимая симуляция
  src/OpenRTS.Content/       # RTS определения и подготовка контента
  src/OpenRTS.Godot/         # Адаптер Godot
  libs/DeclarativeContent/  # Переиспользуемая MIT библиотека
  tools/OpenRTS.Headless/   # Сценарии, реплеи, измерения
  tests/                    # Проверки ядра и контента
  sandbox/                  # Минимальный Godot проект
  docs/                     # Решения, исследования и инструкции
```

Это схема, а не перечень уже существующих проектов. Контентный модуль выделяется только при наличии кода; отдельные Audio, Rendering.Abstractions, Network и общий DI контейнер заранее не создаются.

Планируемая самостоятельная GPL игра может получить соседний каталог `OpenRTS.CncDemo`. Она будет потребителем упакованного ядра. Публичное имя, размещение и момент её создания пока не определены. Не нужно создавать пустой репозиторий заранее. Новый каталог за пределами текущих разрешённых корней потребует расширения доступа; публикация на GitHub является отдельным действием.

**Этап 1. Воспроизводимая сборка и границы проектов.** Создать минимальный solution, ядро, headless приложение, тестовый проект и Godot стенд. Зафиксировать проверенные версии инструментов и команды build/test/run/verify. Настроить игнорирование генерируемых файлов, затем локальный Git репозиторий. Автоматическая публикация, push и внешний CI пока не требуются.

Перенести DeclarativeContent из Hyperfleets вместе с LICENSE, README и тестами, без bin/obj и Godot metadata. Зафиксировать исходный commit и путь, если исходник находится под Git; иначе записать контрольные суммы. Исходный Hyperfleets не изменять. Первая интеграция использует локальную копию с известным происхождением; общий NuGet пакет или отдельный репозиторий библиотеки выделяется при необходимости синхронных обновлений двух игр.

Критерии готовности: чистая сборка и запуск тестов из документированной команды, работающий минимальный Godot стенд, одинаковая загрузка простого набора определений в headless и Godot, отсутствие Godot зависимостей у ядра. Достаточно диагностического экрана; игровые механики здесь не нужны.

**Этап 2. Минимальная симуляция и её граница с Godot.** Перед реализацией сравнить варианты численного представления, выбрать координаты и записать короткое архитектурное решение. Реализовать фиксированный тик, устойчивые ID, упорядоченные команды, RNG и простой мир с создаваемыми и удаляемыми сущностями.

Организовать отдельный поток симуляции и передачу опубликованных кадров. Движение на этом этапе может быть простым, без поиска пути. Godot принимает команды ввода и показывает примитивы с интерполяцией. Предусмотреть корректную остановку потока, обработку ошибки и повторный запуск сценария.

Критерии готовности: один журнал команд даёт одинаковый результат в headless и Godot; FPS представления не меняет состояние; публикация кадров не создаёт гонок; пропуск кадров не теряет обязательные события; остановка приложения завершает исполнителей без зависания.

**Этап 3. Навигация и параллельное исполнение.** Исследовать сеточную навигацию, размеры юнитов, динамические препятствия и движение групп. Выбрать правила конфликтов и момент применения фоновых результатов. Начать с A* и понятных правил прохода через узкие места. Создать последовательный и параллельный режимы реальной вычислительной подсистемы, например пакетного поиска маршрутов.

Критерии готовности: сценарии с препятствиями и узким проходом воспроизводимы при разном количестве рабочих потоков и порядке завершения задач. Потоки не меняют выдачу ID, RNG и разрешение конфликтов. Измеряются время тика, ожидание работников, длина очередей, стоимость передачи данных и выделения памяти. Параллельность оценивается относительно последовательного режима на одинаковой нагрузке.

**Этап 4. Один законченный игровой сценарий.** Добавить здоровье, приказы движения и атаки, простое оружие, ресурс и очередь производства. Использовать явные задачи юнитов и системы массовых операций. Конкретный баланс и внешний вид остаются в стендовом наборе правил.

Критерии готовности: можно создать группу, провести её через препятствия, атаковать цель и произвести новый юнит. UI передаёт команды, а не меняет мир напрямую. Сценарий полностью воспроизводится без Godot.

**Этап 5. Сохранение и диагностика воспроизводимости.** Подготовить полный снимок состояния и восстановление, включающие отложенные действия, RNG и правила восстановления незавершённых задач. Добавить сравнение состояний с указанием первого различия. Версионировать формат сохранения и журнал команд без обещания совместимости всех будущих версий.

Критерии готовности: непрерывный запуск и запуск с сохранением и восстановлением дают одинаковое дальнейшее состояние. Ошибка воспроизводится из сценария, начальных данных и команд. Хеши не зависят от процессных хешей .NET. При расхождении можно определить первый тик и подсистему.

**Этап 6. Масштабирование и первый внешний потребитель.** По измерениям оптимизировать навигацию, пространственные индексы, цели, видимость и представление. После стабилизации реальных контрактов собрать пакет ядра и подключить отдельную игру. Выбор и реализация сетевого модуля начинаются при появлении требований этой игры.

Начальные исследовательские нагрузки — 100, 1000 и 10000 сущностей. Это профили экспериментов, не обещание заданного FPS. Для каждого результата сохраняются оборудование, конфигурация сцены, число активных сущностей и заданий, параметры исполнителя, частота тиков, p50/p95 времени тика, память и время представления. Сравниваются стоящие, движущиеся и воюющие сущности; одно число общего количества юнитов недостаточно.

Критерии готовности: определён воспроизводимый целевой профиль, понятны узкие места, внешняя игра собирается с пакетом без ссылок на внутренние пути исходников. Для будущей GPL игры отдельно учтены зависимости и ассеты.

**Кто принимает решения.** Уже принятые архитектурные договорённости не требуют повторного подтверждения. Разработку, локальные проверки, чтение доступных источников и исправление ошибок можно выполнять самостоятельно. Никакая часть плана не является автоматической командой опубликовать пакет или репозиторий.

До ответа пользователя рабочие гипотезы — desktop, наземная 2.5D симуляция и простое 3D представление геометрическими примитивами; это не обязательства публичного API.
