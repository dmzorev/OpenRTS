# 015. Первый перенос на Frent: E0–E2

Дата: 2026-11-05. **Выполнены baseline, unit identity/lifecycle и перенос производства.** [Решение014](../decisions/014-ecs-foundation.md), [план оставшихся шагов](../research/ecs-selection/migration.md).

## Что изменено

- Core закрепляет Frent0.9.1-beta точным диапазоном, с packages.lock.json. MIT notice копируется в выходные каталоги/пакет; происхождение и hashes — [vendor manifest](../vendor/frent.json).
- SimulationWorld владеет unit storage. В нём UnitIdentity для каждого юнита/здания, ProducerState только у производителей. Frent.World не считается единственным миром всей игры; другие домены могут иметь свои stores либо обычные структуры.
- SortedDictionary производителей удалён. Единственный экземпляр очередей/rally живёт в ProducerState. Закрытая ECS query формирует cached ID order, порядок обработки/публикации/хеша остаётся по стабильному OpenRTS EntityId.
- Spawn выполняется вне открытой query: новая строка/занятость выхода видна следующему производителю. Новый производитель попадает в следующий production-проход. Смерти удаляют ECS membership до производства.
- SimulationWorld теперь IDisposable. Session освобождает мир на owner thread до Completion при успехе, ошибке и выходе через отмену. Прямые потребители используют using; публичные фабрики сценариев освобождают частично созданный мир при ошибке. Published leases продолжают владеть копиями.
- Горячие позиции/движение/бой пока в EntityState[]. Там временно хранится внутренний Frent handle; HP/позиции не дублируются в двух mutable хранилищах. Этот мост удаляется при E4. Definitions/UI Actions остаются E3.

Форматы direct7/nav11/catalog7 сохранены. Frent slot/version/world IDs и порядок компонентов не входят в gameplay hash, команды или кадры.

## Метод измерения

Среда: macOS27.2 arm64,14logical processors, SDK10.0.105/runtime10.0.5, Release, `DOTNET_TieredCompilation=0`. По3 последовательных запуска для каждого размера1000/10000; не одновременно с полным тестовым прогоном или Godot verification. Каждый запуск —3нагрузки,64warm-up тика на отдельном мире,256измеряемых. P50/p95 исключают первый тик; allocations включают его, рост массивов, реальные Spawn и новые repeat tasks.

Нагрузки без terrain navigation, оружия и рендера:

- `units`: все подвижные, один MoveAll. Каталог допускает производителей, но их экземпляров нет.
- `mixed`: каждый20-й объект — неподвижный производитель; остальные — юниты. Каждому производителю назначена своя repeat-задача и rally.
- `production`: все начальные объекты — производители, те же задачи/rally. Выпуск ограничен общими32/тик; выход может быть занят, задача сохраняется.

Длительность производства8тиков, выход фиксированный, search radius0. Это стоимость текущих очередей, motion index и создания объектов, а не тест справедливого распределения общей квоты. После256тиков production1000 содержит8968объектов, production10000 —17968; увеличение числа объектов входит в нагрузку.

Создание мира, retained managed memory после GC, Step, CopyPoses и Report измеряются раздельно. Snapshot/hash — по одному замеру на запуск, поэтому3 значения имеют гораздо меньшую доказательность, чем255 steady tick samples. Общая память процесса/native memory не измерена. Аллокации — current thread; здесь jobs не используются.

## Интерпретация и пределы

По p95 Step первый перенос проходит предварительный10% gate; эти результаты не доказывают ускорение RTS библиотекой. Навигация/бой остаются прежними алгоритмами. Уже эти нагрузки на10000 initial объектов превышают40мс p95 для mixed/production — готовность произвольных10000 боевых юнитов на25Гц не заявляется.

На10000 ordinary units retained managed memory:6.75→7.33МБ; на10000 производителях:11.07→10.65МБ. Это дельта живых managed данных создания мира, не память всего процесса. За256тиков production10000 Step allocations выросли17.08→18.06МБ, mixed10000 —9.10→10.12МБ; workload units остался40560байт, включая первый приказ.

CopyPoses10000: units0.141→0.183мс, mixed1.088→0.594мс, production1.453→0.658мс. Отдельный Report в mixed вырос7.33→8.94мс; это наблюдаемая цена/GC-вариативность старого копирования/сортировки и доступа к новому storage, не улучшение хеширования. Такие одиночные замеры на запуск требуют отдельного профиля перед оптимизацией Report.

Стоимость дополнительной identity/storage пока накладывается на старый горячий массив. Retained память обычных юнитов растёт; удаление SortedDictionary частично или полностью компенсирует это у производителей. Step allocations при создании тысяч новых сущностей возрастают: расширяются и старые массивы с дополнительным handle, и native ECS storage. Это ограниченная структурная работа, а не доказательство новых аллокаций при неизменной membership; отдельный steady allocation guard описан выше.

Report/CopyPoses остаются отдельными затратами: чтение producer-компонента убрало повторный поиск ID, но старый Report всё ещё копирует/сортирует широкие EntityState. Не трактуем замеры snapshot/hash как полноценный профиль сохранений или повод обновлять golden state hashes. E3 отделяет definitions/UI, E4 переносит горячие срезы и устраняет временный мост; N4 решает навигационные пики независимо от ECS.

## Воспроизведение

```sh
./tools/dev.sh test
./tools/dev.sh test --filter=ECS
./tools/dev.sh benchmark --ecs-benchmark --count=1000 --ticks=256
./tools/dev.sh benchmark --ecs-benchmark --count=10000 --ticks=256
./tools/dev.sh verify
```

Для измерений повторять benchmark последовательно, сохранять JSON и сравнивать одинаковые workload/count/ticks. Restore Core можно отдельно проверить через `dotnet restore src/OpenRTS.Core/OpenRTS.Core.csproj --locked-mode`; остальные Godot SDK/content зависимости сохраняют прежний способ восстановления.
