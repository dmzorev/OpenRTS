# Эксперимент с затухающей видимостью

9 ноября 2026. [Алгоритмы и контракт](../research/fog-visibility/temporal-retention.md). **Результат:** сама задержка недорогая, универсального ускорения от временного кэша нет. На воспроизводимом зигзагообразном пути он ускоряет fog примерно вдвое; на прямой колонне прежний групповой кэш быстрее, на расходящихся путях временной memo существенно хуже. Основной режим по умолчанию оставлен мгновенным.

## Длительности и нагрузка

Исследованы H=0,2,5,12,25,50 при25Гц — от0 до2секунд. Для каждой длительности сравнивались:

- клеточный таймер поверх текущего алгоритма;
- prototype memo точных Owner/X/Y/Radius, сохраняющий вклад ушедшей зоны до истечения H;
- оба варианта с групповым алгоритмом и без него.

Четыре траектории: прямая колонна с pitch1024, плотная прямая колонна с pitch256, зигзаг с pitch1024 и расходящиеся траектории. В колоннах16 дорожек, продвижение128 по пути за тик, radius6144. На зигзаге вертикальное смещение также меняется на128, поэтому физическая длина шага больше прямой; внутри каждого A/B входы идентичны. Ни тел, ни столкновений, ни боя в этом замере нет.

Apple M3 Max, arm64, .NET10.0.105, Release, `DOTNET_TieredCompilation=0`. Замер **только обновления fog и временного memo**, без расчёта траекторий, World.Step в целом, hash, кадров и Godot. 64 прогревочных +80 измеряемых тиков для10 000 источников. Подготовка массива входов вынесена из Stopwatch, GC для оценки heap выполняется до измерения. Основной замер проводился без параллельного тестового/графического прогона.

Сетка1024, два игрока, sources owner1. Ширина мира вычисляется по длине колонны и времени прогона, высота128×1024. Для каждой пары backends карта и входы одинаковы. Это отличается от прежнего `FogGroupBenchmark`, который измерял World.Step, поэтому абсолютные времена нельзя сопоставлять напрямую.

Команда: `./tools/dev.sh benchmark --fog-retention-benchmark --count=10000 --ticks=80`. Прогон на1000 источников/20тиках использован как предварительная проверка всех комбинаций. [Все96 профилей на10 000](fog-retention/10000.txt), [на1000](fog-retention/1000.txt).

## Результаты с включённым штатным групповым кэшем

p50 fog update, миллисекунды:

| H | Секунды | Прямая: таймер | Прямая: memo | Зигзаг: таймер | Зигзаг: memo |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | 0.308 | 9.968 | 6.029 | 10.002 |
| 2 | 0.08 | 0.307 | 11.629 | 6.024 | 12.070 |
| 5 | 0.20 | 0.307 | 13.950 | 6.004 | 14.527 |
| 12 | 0.48 | 0.311 | 2.993 | 6.062 | 3.052 |
| 25 | 1.00 | 0.311 | 3.010 | 6.091 | 3.083 |
| 50 | 2.00 | 0.306 | 3.016 | 6.041 | 3.091 |

У прямой колонны общий сдвиг уже позволяет использовать фазовую групповую маску; временная история для ускорения не нужна. Зигзаг нарушает постоянство относительных смещений участников, но сохраняет повторное прохождение точных геометрических точек. Следующий юнит приходит примерно через8 тиков. H=5 не доживает до полезного повторения, H=12 уже доживает. После этого увеличение срока почти не улучшает скорость.

Для зигзага H=12 p95: **6.400 →3.221мс**, p50 примерно **1.99× быстрее**. Цена по удерживаемому managed heap в прогревочном снимке: около **4.77 →34.74MiB**. При H=50 memo уже около46.78MiB. Heap — оценка managed состояния после прогрева, не RSS/VRAM и не пик.

На плотной прямой колонне pitch256 H=2 уже даёт reuse, но memo всё равно проигрывает текущему групповому алгоритму: около1.275мс против0.308мс без удержания. Это показывает, что достаточный TTL сам по себе не гарантирует выгоды.

В расходящемся профиле H=50: клеточный таймер около6.593мс, memo32.071мс; heap примерно4.74MiB против178.83MiB, до509917 геометрических записей. У memo появляются существенные аллокации: около1.33MB/тик в этом grouped-профиле. Клеточный вариант в этих изолированных замерах обходится без аллокаций на тик. Prototype не оптимизирован пулами, поэтому этот результат не доказывает невозможность иного временного алгоритма; он исключает безусловную замену текущего кэша этим вариантом.

## Корректность

- 12 randomized traces (6 сроков ×2 режима группировки),90 тиков каждый: все клетки двух игроков сравниваются после каждого обновления клеточного reference и memo. Проверяются случайные исчезновения, смена владельца/радиуса, повторные зоны и крайние обрезанные клетки.
- Все48 измеренных A/B-пар на10 000 завершились одинаковым digest статусов карты; то же для предварительного прогона1000. Совпадение проверяется в самом benchmark, расхождение завершает его ошибкой.
- **12 Fog checks прошли**, включая истечение без движения и после удаления всех источников, точную границу срока, повторное раскрытие, различие владельцев, hash срока/будущего состояния, совпадение группового и индивидуального режима с удержанием, яркость и независимость старого lease.
- Полный прогон: **304 OpenRTS checks passed, 0 failed**. Debug solution и Release headless собраны без warnings/errors. Полный `tools/verify.py` прошёл для прежнего H=0.

Hash-совпадение между разными H не требуется: это разные игровые правила. В сравнении backends при одинаковом H сравниваются видимость и история, а не внутренние synthetic IDs.

## Визуальная проверка

Godot `--verify-fog --realtime --fog-hold=50` прошёл с графическим окном. [Снимок кругового следа](fog-retention/hold-50.png) просмотрен: след темнеет постепенно, текущий обзор остаётся круговым, неизвестная область сохраняет квадраты. Клеточные швы первой попытки устранены декоративной ping-pong историей маски; точная сетка использует byte-яркость из симуляции. Это две визуализации одного игрового эксперимента, а не два источника игровой истины.

Маска кругового следа сбрасывается при смене наблюдателя/времени/длительности. При пропущенных кадрах вычитается прошедшее число тиков, но не восстанавливаются неотрисованные промежуточные круги. Поэтому её граница может отличаться от реальной видимости клеток; объекты/приказы фильтруются последней. GPU-стоимость дополнительных viewport и цена публикации яркости в замер fog update не входят и отдельно не профилировались.

## Практический вывод

Эксперимент доступен: `./tools/dev.sh run --fog --fog-hold=12`, например0.48секунды; H=50 даёт2секунды. Флаг можно также передать основному матчу. По умолчанию H=0, в меню новая игровая policy автоматически не включалась.

Для ощущения затухания можно оценивать5–12тиков без ожидания ускорения. Временной геометрический memo имеет смысл продолжать исследовать как адаптивный backend для повторяющихся извилистых колонн, после решения о допустимости самой задержки видимости.25–50тиков не показали дополнительного выигрыша на таком пути и увеличили память. Нужен отдельный полный профиль симуляции/кадров/GPU перед производственным подключением.
